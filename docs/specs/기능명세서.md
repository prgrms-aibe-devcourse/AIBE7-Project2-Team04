## FR-01. 회원 관리

| ID | 요구사항 | 우선순위 | 구현 방식 |
| --- | --- | --- | --- |
| FR-01-01 | 사용자는 회원가입을 할 수 있어야 한다. | 필수 | Spring Security `PasswordEncoder`로 비밀번호를 해싱한 뒤 `users` 테이블에 저장하며 원문 비밀번호는 저장하거나 로그에 남기지 않음 |
| FR-01-02 | 사용자는 로그인 및 로그아웃을 할 수 있어야 한다. | 필수 | 이메일 로그인은 `AuthenticationManager`, 카카오·Google 로그인은 OAuth2 Client로 인증한다. `users.provider`와 `provider_id`로 가입 방식을 식별하며 성공 시 자체 서명한 단기 Access Token과 교체 가능한 Refresh Token을 발급하고, 로그아웃 시 Refresh Token을 폐기 |
| FR-01-03 | 사용자는 회원탈퇴를 할 수 있어야 한다. | 필수 | `users.status = withdrawn` 처리, 개인정보 마스킹, 해당 사용자의 Refresh Token 전체 폐기 후 이후 로그인과 API 접근을 차단. 하드 삭제 시점은 데이터 보존 정책에 따라 별도 처리 |
| FR-01-04 | 사용자는 자신의 프로필 정보를 조회할 수 있어야 한다. | 필수 | Spring Boot REST API (`GET /api/users/me`), JWT의 sub 클레임으로 본인 조회만 허용 |
| FR-01-05 | 사용자는 닉네임, 프로필 이미지, 관심사 등의 정보를 수정할 수 있어야 한다. | 필수 | `PATCH /api/users/me`. 프로필 이미지는 Supabase Storage에 업로드 후 URL만 `users` 테이블에 저장 |
| FR-01-06 | 인증되지 않은 사용자는 매칭, 채팅 등 회원 전용 기능을 사용할 수 없어야 한다. | 필수 | Spring Security의 인증 필터 체인에서 JWT 미존재/만료 시 `401 Unauthorized` 반환, 회원 전용 엔드포인트는 `@PreAuthorize("isAuthenticated()")` 적용 |
| FR-01-07 | 시스템은 사용자별 권한을 구분하여 접근을 제어해야 한다. | 필수 | 서버가 발급하는 JWT에 `roles` 클레임을 포함하고 Spring Security Authority로 변환하여 `@PreAuthorize("hasRole(...)")`로 API 단위 권한 제어 |
| FR-01-08 | 시스템은 OAuth 가입 시 이메일과 프로필 예외를 일관되게 처리해야 한다. | 필수 | Google은 검증된 이메일, 카카오는 유효하고 검증된 이메일만 허용한다. 이메일 없음·미검증 시 가입 실패, 다른 Provider의 동일 이메일은 자동 연결 없이 기존 방식 안내, 닉네임 없음·중복 시 임시 닉네임 생성 후 `profileSetupRequired`로 프로필 수정을 유도 |
| FR-01-09 | 사용자는 가입 완료 후 선택형 온보딩에서 자가 응답 기반 식사·대화 성향을 설정할 수 있어야 한다. | 선택 | 가입 성공을 막지 않는 건너뛰기 가능한 설문으로 제공한다. V1은 정형 카드·태그·음식 카테고리를 버전된 규칙으로 처리하고, 자유 서술과 Spring AI 분석은 명시적 동의를 전제로 한 2차 확장으로 분리한다. 이를 심리 진단으로 표현하지 않는다. |
| FR-01-10 | 사용자는 자신의 성향 프로필과 상대방 선호 중요도를 조회·수정·초기화할 수 있어야 한다. | 필수 | `user_personality_profiles`, `user_personality_answers`, `user_personality_embeddings`, `user_matching_preferences`를 사용자 도메인 하위에서 분리 관리한다. 수정 시 점수와 임베딩을 재생성하고, 초기화 시 파생 데이터까지 삭제한다. |

## FR-03. 실시간 매칭

| ID | 요구사항 | 우선순위 | 구현 방식 |
| --- | --- | --- | --- |
| FR-03-01 | 회원은 실시간 매칭을 요청할 수 있어야 한다. | 필수 | `POST /api/matches/realtime`, 요청 시 Redis에 대기 상태 등록 (`match:waiting:{requestId}`) |
| FR-03-02 | 사용자는 구 단위 기본 활동지역을 선택하고, 해당 구를 중심으로 열린 지도에서 핀을 지정하여 매칭 기준 위치를 설정할 수 있어야 한다. | 필수 | `user_location_preferences`에는 행정구역 코드·표시명만 저장한다. 매칭 요청에는 선택한 구와 핀 위경도를 전달하고 서버가 경도·위도 순서의 `geography(Point, 4326)`로 생성한다. Geolocation API는 필수 의존성이 아니다. |
| FR-03-03 | 사용자는 원하는 식사 시간대를 설정할 수 있어야 한다. | 필수 | Redis 대기 정보에 `desiredTimeRange` 포함, 후보 탐색 시 시간대 겹침 여부로 필터링 |
| FR-03-05 | 시스템은 매칭 대기 중인 사용자의 상태를 관리해야 한다. | 필수 | Redis TTL로 대기 상태 자동 관리 (`waiting → matched/cancelled/expired`) |
| FR-03-06 | 시스템은 위치, 시간, 성향 등의 조건을 기반으로 적합한 1명의 사용자를 탐색해야 한다. | 필수 | **1단계(하드 필터)**: PostGIS `ST_DWithin`으로 반경 내 후보 조회 + 시간대·대기 상태·차단 관계 필터. **2단계(결정론적 소프트 랭킹)**: 버전된 호환도 공식으로 정형 성향 점수와 요청자의 선호 중요도를 계산. **3단계(AI 보조 랭킹)**: 자유 서술 임베딩 유사도를 제한된 가중치로 합산한다. AI가 후보 적격 여부를 단독 결정하지 않는다. |
| FR-03-07 | 매칭이 성사되면 참여 사용자에게 매칭 결과를 실시간으로 전달해야 한다. | 필수 | 매칭 확정 시 WebSocket + STOMP로 `/topic/matches/{requestId}` 구독자에게 push |
| FR-03-08 | 사용자는 매칭 대기 중 요청을 취소할 수 있어야 한다. | 필수 | `DELETE /api/matches/realtime/{requestId}`, Redis 키 즉시 삭제 |
| FR-03-09 | 일정 시간이 지나도 매칭되지 않은 요청은 자동 만료될 수 있어야 한다. | 선택 | Redis 키 TTL 설정(예: 15분)으로 자동 만료 처리, 만료 시 이벤트 리스너에서 사용자에게 알림 |
| FR-03-10 | 동일 사용자가 동시에 여러 매칭에 중복 참여하지 못하도록 제한할 수 있어야 한다. | 필수 | Redis에 `match:user:{userId}` 키로 현재 대기 중인 requestId 기록, 신규 요청 시 존재 여부 확인 후 `409 Conflict` 반환 |
| FR-03-11 | 시스템은 사용자 성향과 상대방 선호 중요도를 반영한 설명 가능한 호환도 점수로 후보를 정렬해야 한다. | 선택 | 대화량·식사속도·계획성·새로운 음식 선호 등 차원별로 `유사 선호` 또는 `보완 선호` 규칙을 적용하고 중요도 가중합을 계산한다. 시스템 기본 가중치와 산식 버전을 관리하며 사용자에게는 상위 호환 사유만 노출한다. |
| FR-03-12 | AI 또는 임베딩 기능에 장애가 발생하거나 성향 프로필이 없는 경우에도 기본 조건 매칭은 정상 동작해야 한다. | 필수 | 임베딩 생성과 AI 분석은 비동기로 격리하고 실패 시 정형 성향 점수만, 정형 점수도 없으면 하드 필터 결과만으로 fallback한다. 요청별 LLM 동기 호출을 필수 경로에 두지 않는다. |

## FR-04. 위치 기능

| ID | 요구사항 | 우선순위 | 구현 방식 |
| --- | --- | --- | --- |
| FR-04-01 | 시스템은 사용자가 선택한 구 단위 활동지역과 지도 핀의 위도·경도를 구분하여 처리할 수 있어야 한다. | 필수 | 활동지역은 안정적인 행정구역 코드와 표시명으로 저장하고, 세부 위치는 필요한 요청·게시글에만 PostGIS `geography(Point, 4326)`로 저장한다. |
| FR-04-03 | 시스템은 특정 반경 내에 있는 매칭 후보를 조회할 수 있어야 한다. | 필수 | 실시간 매칭 대기열에도 동일한 PostGIS 반경 쿼리 적용 |

| FR-04-05 | 시스템은 사용자들이 선택한 희망 매칭 장소 핀 간 거리를 계산할 수 있어야 한다. | 필수 | PostGIS `ST_Distance`로 두 사용자의 선택 핀 간 거리를 계산하고 실제 사용자 간 실시간 거리로 표현하지 않는다. |
| FR-04-06 | 위치 정보는 사용자의 동의를 받은 경우에만 수집되어야 한다. | 필수 | `user_location_preferences.location_service_consent`로 선택 지역·핀 저장 동의를 관리한다. 미동의 시 위치 기반 API는 `403 Forbidden`이며 `users`에는 실시간 위치를 저장하지 않는다. |
| FR-04-07 | 시스템은 Geolocation API 없이 구 단위 활동지역의 대표 좌표로 지도를 초기화하고 사용자가 핀으로 세부 위치를 확정할 수 있어야 한다. | 필수 | 최초에는 구 선택 UI를 제공하고, 이후에는 저장된 `region_code`에 대응하는 대표 좌표로 Kakao Maps 지도를 연다. 지도 클릭·마커 이동 이벤트에서 핀 위경도를 얻는다. |
| FR-04-08 | 시스템은 선택한 핀이 선택한 구에 속하는지 검증하고 거리 기준을 명확히 표시해야 한다. | 필수 | Kakao 좌표→행정구역 API 또는 서버가 관리하는 행정구역 경계 데이터로 핀의 구 코드를 검증한다. 불일치 시 `LOCATION_002`를 반환하고 프론트엔드는 선택 구 변경 또는 핀 재지정을 안내한다. |

## FR-08. AI 추천

| ID | 요구사항 | 우선순위 | 구현 방식 |
| --- | --- | --- | --- |
| FR-08-01 | 사용자는 매칭 조건을 기반으로 식당 추천을 요청할 수 있어야 한다. | 선택 | `POST /api/ai/restaurant-recommendations`, 채팅방 대화 내용 또는 별도 입력값을 요청 본문으로 전달 |
| FR-08-02 | 시스템은 두 사용자의 희망 지역, 음식 종류, 예산 등의 정보를 활용하여 적절한 식당을 추천할 수 있어야 한다. | 선택 | **1단계**: Spring AI로 대화/입력 텍스트에서 지역·음식종류·예산을 구조화 JSON으로 파싱 → 공공데이터/카카오맵 API에서 필터링. 인원은 1:1 매칭의 두 명으로 고정한다. **2단계**: 외부 식당 정보로 생성한 `restaurant_embeddings`를 요청 임베딩과 비교해 보조 재정렬한다. 임베딩이 없거나 AI 장애 시 1단계 결과를 유지한다. |
| FR-08-03 | AI 추천 기능에 장애가 발생하더라도 기본 매칭 기능은 정상적으로 사용할 수 있어야 한다. | 필수 | AI 추천 로직을 별도 서비스/모듈로 분리, 예외 발생 시 매칭·채팅 플로우와 독립적으로 fallback(빈 결과 또는 기본 필터 결과) 반환. Circuit Breaker(Resilience4j) 적용 권장 |
| FR-08-04 | AI가 생성한 추천 결과임을 사용자에게 구분하여 표시해야 한다. | 선택 | 응답에 `is_ai_generated: true` 플래그 포함, 프론트엔드에서 "AI 추천" 배지 표시. 1단계(필터만)와 2단계(후기 기반 재정렬) 결과도 구분 표시 |

## FR-09. 마이페이지

| ID | 요구사항 | 우선순위 | 구현 방식 |
| --- | --- | --- | --- |
| FR-09-01 | 사용자는 자신의 프로필을 조회할 수 있어야 한다. | 필수 | `GET /api/mypage/profile`, JWT sub로 본인 데이터만 조회 |

## 공통 처리 원칙

| 항목 | 내용 |
| --- | --- |
| 인증 방식 | Spring Security가 이메일·비밀번호 및 카카오·Google OAuth2 로그인을 직접 처리한다. 계정당 하나의 가입 방식만 허용하고 동일 이메일의 다른 Provider 계정을 자동 연결하지 않는다. 서버가 환경변수로 관리하는 공통 비밀키와 HS256(HMAC-SHA256) 알고리즘으로 Access Token을 발급·검증하며, Refresh Token은 해시하여 DB에 저장하고 재발급 시 회전시킨다. JWT 검증 시 허용 알고리즘을 HS256으로 제한하고 `iss`, `aud`, `exp` 클레임을 검증한다. |
| OAuth 가입 예외 | OAuth 이메일 없음·미검증은 가입 실패로 처리한다. 동일 이메일의 다른 Provider 가입은 자동 연결하지 않고 기존 방식을 안내한다. 닉네임이 없거나 중복되면 무작위 임시 닉네임을 생성하고 최초 토큰 교환 응답의 `profileSetupRequired`로 프로필 수정 화면 이동을 유도한다. |
| 성향 데이터 원칙 | 성향은 자가 응답 기반 식사·대화 선호로 한정하고 심리 진단이나 민감 특성을 추론하지 않는다. 온보딩은 건너뛸 수 있어야 하며 사용자가 결과를 조회·수정·초기화할 수 있어야 한다. 나의 성향과 원하는 상대의 중요도는 별도로 저장한다. |
| 임베딩 사용 원칙 | 필수 조건(위치/시간 등 명확한 값)은 항상 하드 필터로 처리하고, 벡터 유사도는 "성향/분위기/자유 텍스트"처럼 모호한 선호도를 다루는 보조 랭킹 수단으로만 사용한다. 모델명·차원·소스 버전을 함께 관리하고 서로 다른 모델의 벡터를 직접 비교하지 않는다. |
| 장애 격리 | AI/임베딩 관련 기능은 모두 핵심 매칭·채팅 플로우와 분리하여, 실패 시에도 기본 기능은 영향받지 않도록 설계 |
| API 문서화 | Springdoc OpenAPI(Swagger)로 전 엔드포인트 자동 문서화 |
| 모니터링 | Prometheus + Grafana로 매칭 대기열 크기, 매칭 성사율, AI 응답 지연/실패율, WebSocket 연결 수 등 추적 |
