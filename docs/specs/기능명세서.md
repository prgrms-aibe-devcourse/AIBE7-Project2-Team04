## FR-01. 회원 관리

| ID | 요구사항 | 우선순위 | 구현 방식 |
| --- | --- | --- | --- |
| FR-01-01 | 사용자는 회원가입을 할 수 있어야 한다. | 필수 | Spring Security `PasswordEncoder`로 비밀번호를 해싱한 뒤 `users` 테이블에 저장하며 원문 비밀번호는 저장하거나 로그에 남기지 않음 |
| FR-01-02 | 사용자는 로그인 및 로그아웃을 할 수 있어야 한다. | 필수 | 이메일 로그인은 `AuthenticationManager`, 카카오·Google 로그인은 OAuth2 Client로 인증한다. `users.provider`와 `provider_id`로 가입 방식을 식별하며 성공 시 자체 서명한 단기 Access Token과 교체 가능한 Refresh Token을 발급하고, 로그아웃 시 Refresh Token을 폐기 |
| FR-01-03 | 사용자는 회원탈퇴를 할 수 있어야 한다. | 필수 | `users.status = withdrawn` 처리, 개인정보 마스킹, 해당 사용자의 Refresh Token 전체 폐기 후 이후 로그인과 API 접근을 차단. 하드 삭제 시점은 데이터 보존 정책에 따라 별도 처리 |
| FR-01-04 | 사용자는 자신의 프로필 정보를 조회할 수 있어야 한다. | 필수 | Spring Boot REST API (`GET /users/me`), JWT의 sub 클레임으로 본인 조회만 허용 |
| FR-01-05 | 사용자는 닉네임, 프로필 이미지, 관심사 등의 정보를 수정할 수 있어야 한다. | 필수 | `PATCH /users/me`. 프로필 이미지는 Supabase Storage에 업로드 후 URL만 `users` 테이블에 저장 |
| FR-01-06 | 인증되지 않은 사용자는 매칭, 채팅 등 회원 전용 기능을 사용할 수 없어야 한다. | 필수 | Spring Security의 인증 필터 체인에서 JWT 미존재/만료 시 `401 Unauthorized` 반환, 회원 전용 엔드포인트는 `@PreAuthorize("isAuthenticated()")` 적용 |
| FR-01-07 | 시스템은 사용자별 권한을 구분하여 접근을 제어해야 한다. | 필수 | 서버가 발급하는 JWT에 `roles` 클레임을 포함하고 Spring Security Authority로 변환하여 `@PreAuthorize("hasRole(...)")`로 API 단위 권한 제어 |
| FR-01-08 | 시스템은 OAuth 가입 시 이메일과 프로필 예외를 일관되게 처리해야 한다. | 필수 | Google은 검증된 이메일, 카카오는 유효하고 검증된 이메일만 허용한다. 이메일 없음·미검증 시 가입 실패, 다른 Provider의 동일 이메일은 자동 연결 없이 기존 방식 안내, 닉네임 없음·중복 시 임시 닉네임 생성 후 `profileSetupRequired`로 프로필 수정을 유도 |
| FR-01-09 | 사용자는 가입 완료 후 선택형 온보딩에서 자가 응답 기반 식사·대화 성향을 설정할 수 있어야 한다. | 선택 | 가입 성공을 막지 않는 건너뛰기 가능한 설문으로 제공한다. 정형 카드·태그·음식 카테고리를 버전된 규칙으로 처리하며, 최대 300자 자유 서술과 Spring AI 분석은 명시적 동의를 전제로 한다. AI 추천 태그는 사용자가 확정하기 전 저장하지 않는다. 이를 심리 진단으로 표현하지 않는다. |
| FR-01-10 | 사용자는 자신의 성향 프로필을 조회·수정·초기화할 수 있어야 한다. | 필수 | `user_personality_profiles`, `user_personality_answers`, `user_personality_embeddings`를 성향 도메인에서 관리한다. 동의한 자기소개가 있으면 자기소개 자유 텍스트만 공통 버전 문서로 만들어 비동기 임베딩한다. 자기소개를 재제출하면 기존 임베딩을 먼저 제거하고 최신 텍스트 이벤트만 저장하며, 이벤트 처리 중 원문이 수정·삭제된 경우 이전 결과를 저장하지 않는다. 카드 점수와 확정 태그는 임베딩 문서에 포함하지 않는다. 동의 철회·초기화 시 원문과 파생 임베딩을 삭제한다. 상대방 선호는 성향 조사에 포함하지 않는다. |

## FR-03. 실시간 매칭

| ID | 요구사항 | 우선순위 | 구현 방식 |
| FR-03-01 | 회원은 실시간 매칭을 요청할 수 있어야 한다. | 필수 | `POST /matches/realtime/requests`, 음식 카테고리·미래 식사 일시·구·핀·반경·희망 태그 3~5개와 선택형 설명을 받아 DB와 Redis 5분 TTL 대기 키에 등록한다. 응답은 `requestId`, `WAITING`, `expiresAt`을 포함한다. |
| FR-03-02 | 사용자는 구 단위 기본 활동지역을 선택하고, 해당 구를 중심으로 열린 지도에서 핀을 지정하여 매칭 기준 위치를 설정할 수 있어야 한다. | 필수 | 위치 서비스 동의와 기본 활동지역 일치를 확인하고 `regions`로 표시명을 정규화한다. Kakao 좌표→행정구역 API로 핀 소속을 검증한 뒤 경도·위도 순서의 `geography(Point, 4326)`로 생성한다. Geolocation API는 필수 의존성이 아니다. |
| FR-03-03 | 사용자는 원하는 식사 시간대를 설정할 수 있어야 한다. | 필수 | 미래의 `desiredTimeSlot`을 `match_requests.meal_at`에 저장하고 후보 탐색 시 ±30분 조건에 사용한다. |
| FR-03-05 | 시스템은 매칭 대기 중인 사용자의 상태를 관리해야 한다. | 필수 | Redis 요청 키·Geo 멤버의 TTL과 PostgreSQL `MatchRequest.status`를 함께 관리한다. 취소·제안 진입·매칭 완료 시 커밋 후 대기 키를 제거하고, TTL 만료 또는 키 유실은 주기적 보정 작업에서 `EXPIRED` 처리하거나 남은 대기 시간을 기준으로 복구한다. |
| FR-03-06 | 시스템은 위치, 시간, 성향 등의 조건을 기반으로 적합한 1명의 사용자를 탐색해야 한다. | 필수 | **1단계(하드 필터)**: PostGIS `ST_DWithin`으로 양쪽 요청 핀의 각 탐색 반경을 모두 만족하는 `WAITING` 후보를 조회하고, 자기 요청·동일 사용자·±30분 초과 요청을 제외한다(차단 관계는 MVP 제외). 하드 필터 결과가 없으면 랭킹을 호출하지 않는다. **2단계(결정론적 소프트 랭킹)**: 요청 희망 태그와 후보자의 가입 후 확정 성향 태그를 비교한다. **3단계(AI 보조 랭킹)**: 요청의 자유 서술과 후보자의 본인 성향 임베딩 유사도를 제한된 가중치로 합산한다. 성향 데이터를 계산할 수 있는 후보를 최종 점수 내림차순으로 정렬하고, 계산할 수 없는 후보는 거리·대기 시작 시각·요청 ID 순으로 fallback한다. AI가 후보 적격 여부를 단독 결정하지 않는다. 요청 커밋 직후 탐색과 함께 `WAITING` 요청을 ID 커서 기반으로 5초마다 재탐색한다. 상태가 이미 변경된 요청은 건너뛰고 일시적인 저장소 오류는 다음 주기에 재시도하며, 재시도 범위는 요청의 5분 대기 TTL로 제한한다. |
| FR-03-07 | 매칭이 성사되면 참여 사용자에게 매칭 결과를 실시간으로 전달해야 한다. | 필수 | 양쪽 수락 후 요청 ID 오름차순 잠금으로 `matches`·참여자 2명·`chat_rooms`를 하나의 DB 트랜잭션에 저장하고, 커밋 후 WebSocket + STOMP로 `/user/queue/match-result` 구독자에게 사용자별 결과를 push한다. WebSocket 핸드셰이크에서 Access Token 쿠키를 검증하고 개인 매칭 큐는 인증된 세션만 구독할 수 있다. 연결 유실 시 `GET /matches/realtime/results/latest`로 참여자 본인의 최신 결과를 복구 조회한다. |
| FR-03-08 | 사용자는 매칭 대기 중 요청을 취소할 수 있어야 한다. | 필수 | `DELETE /matches/realtime/requests/{requestId}`에서 소유권과 상태를 잠금 검증하고 DB 커밋 후 Redis 키를 삭제한다. |
| FR-03-09 | 일정 시간이 지나도 매칭되지 않은 요청은 자동 만료될 수 있어야 한다. | 선택 | Redis 요청 키에 5분 TTL을 설정하고, 주기적 보정 작업이 키 만료를 감지하여 PostgreSQL 상태를 `EXPIRED`로 변경한 뒤 요청 키·Geo 멤버를 정리한다. |
| FR-03-10 | 동일 사용자가 동시에 여러 매칭에 중복 참여하지 못하도록 제한할 수 있어야 한다. | 필수 | Redis `SET NX`로 `match:user:{userId}` 예약을 원자 생성하고 DB 저장 후 requestId로 활성화한다. 실패 시 보상 해제하며 중복은 `409 MATCHING_003`을 반환한다. |
| FR-03-11 | 시스템은 매칭 시작 전에 입력한 원하는 상대의 태그·자유 텍스트를 반영한 설명 가능한 호환도 점수로 후보를 정렬해야 한다. | 선택 | 가입 후 성향 조사는 본인의 성향 프로필만 저장한다. 매칭 요청의 희망 태그·자유 텍스트는 상대방의 확정 태그·동일한 텍스트 전용 성향 임베딩과 비교하며 별도의 차원별 중요도 설정은 받지 않는다. 응답에는 최종 점수와 방향별 상위 일치 태그·사용자용 사유만 포함하고 원문·임베딩·차원별 내부 점수는 노출하지 않는다. 카드 점수는 이번 산식에 포함하지 않는다. |
| FR-03-12 | AI 또는 임베딩 기능에 장애가 발생하거나 성향 프로필이 없는 경우에도 기본 조건 매칭은 정상 동작해야 한다. | 필수 | 임베딩 생성과 AI 분석은 비동기로 격리하고 실패·오래된 이벤트·요청 삭제·동의 철회 시 태그 점수를 100%로 재정규화하며, 태그 점수도 없으면 하드 필터 결과와 기본 조건 점수로 fallback한다. 자유 텍스트가 비어 있으면 임베딩 이벤트를 발행하지 않는다. 요청별 LLM 동기 호출을 필수 경로에 두지 않고 AI 점수만으로 후보를 탈락시키지 않는다. 구버전 임베딩은 새 산식에서 제외하며, 동의와 자기소개가 유지된 대상만 점진적으로 재생성한다. AI·성향 Fallback은 정상 매칭 흐름으로 처리하고 Redis 최초 등록 실패만 `503 MATCHING_007`로 구분한다. |
| FR-03-13 | 후보 제안이 생성되면 양쪽 사용자에게 프로필 확인과 동일한 응답 제한 시간을 실시간으로 전달해야 한다. | 필수 | 제안 저장 트랜잭션 커밋 이후 인증된 사용자의 `/user/queue/match-proposal` 개인 목적지로 사용자별 상대 프로필·호환도·동일한 `expiresAt`을 STOMP push한다. 상대 프로필은 공개 필드만 포함하고 정밀 핀·내부 성향 데이터·상대 결정과 응답 시각은 최종 결과 전에 노출하지 않는다. |

## FR-04. 위치 기능

| ID | 요구사항 | 우선순위 | 구현 방식 |
| --- | --- | --- | --- |
| FR-04-01 | 시스템은 사용자가 선택한 구 단위 활동지역과 지도 핀의 위도·경도를 구분하여 처리할 수 있어야 한다. | 필수 | 활동지역은 안정적인 행정구역 코드와 표시명으로 저장하고, 세부 위치는 필요한 요청·게시글에만 PostGIS `geography(Point, 4326)`로 저장한다. |
| FR-04-03 | 시스템은 특정 반경 내에 있는 매칭 후보를 조회할 수 있어야 한다. | 필수 | 실시간 매칭 대기열에도 동일한 PostGIS 반경 쿼리 적용 |
| FR-04-04 | 사용자는 매칭 검색 반경을 설정할 수 있어야 한다. | 선택 | 화면은 기본 3km로 탐색하고, 대기 종료 시 후보가 없으면 `주변에 후보가 없어요. 탐색 반경을 넓혀볼까요?` 안내와 `네`·`매칭 취소` 선택지를 제공한다. `네`를 누르면 기존 조건으로 5km 재탐색을 시작하며 10km 확장은 제공하지 않는다. |
| FR-04-05 | 시스템은 사용자들이 선택한 희망 매칭 장소 핀 간 거리를 계산할 수 있어야 한다. | 필수 | PostGIS `ST_Distance`로 두 사용자의 선택 핀 간 거리를 계산하고 실제 사용자 간 실시간 거리로 표현하지 않는다. |
| FR-04-06 | 위치 정보는 사용자의 동의를 받은 경우에만 수집되어야 한다. | 필수 | `user_location_preferences.location_service_consent`로 선택 지역·핀 저장 동의를 관리한다. 미동의 시 위치 기반 API는 `403 Forbidden`이며 `users`에는 실시간 위치를 저장하지 않는다. 동의를 `false`로 변경하거나 기본 활동지역을 삭제하면 활성 매칭 제안을 생명주기에 따라 취소하고 상대 요청을 복구한 뒤, 본인의 Redis 대기 상태와 활성 요청의 정밀 핀·희망 설명·임베딩을 물리 삭제한다. |
| FR-04-07 | 시스템은 Geolocation API 없이 구 단위 활동지역의 대표 좌표로 지도를 초기화하고 사용자가 핀으로 세부 위치를 확정할 수 있어야 한다. | 필수 | 최초에는 구 선택 UI를 제공하고, 이후에는 저장된 `region_code`에 대응하는 대표 좌표로 Kakao Maps 지도를 연다. 지도 클릭·마커 이동 이벤트에서 핀 위경도를 얻는다. |
| FR-04-08 | 시스템은 선택한 핀이 선택한 구에 속하는지 검증하고 거리 기준을 명확히 표시해야 한다. | 필수 | Kakao 좌표→행정구역 API 또는 서버가 관리하는 행정구역 경계 데이터로 핀의 구 코드를 검증한다. 불일치 시 `LOCATION_002`를 반환하고 프론트엔드는 선택 구 변경 또는 핀 재지정을 안내한다. |

## FR-05. 채팅

| ID | 요구사항 | 우선순위 | 구현 방식 |
| --- | --- | --- | --- |
| FR-05-01 | 매칭이 완료된 사용자들 사이에 채팅방이 생성되어야 한다. | 필수 | 매칭 확정 트랜잭션 내에서 `matches` + 정확히 2개의 `match_participants` + `chat_rooms` 레코드를 원자적으로 자동 생성 |
| FR-05-02 | 사용자는 채팅방에서 실시간 메시지를 전송하고 수신할 수 있어야 한다. | 필수 | WebSocket + STOMP. 클라이언트는 `/app/chat/{roomId}`로 전송, `/topic/chat/{roomId}` 구독으로 수신 |
| FR-05-03 | 사용자는 자신이 참여한 채팅방 목록을 조회할 수 있어야 한다. | 필수 | `GET /chatrooms`, `chat_rooms.match_id`를 통해 `match_participants` 조인 조회 |
| FR-05-04 | 사용자는 채팅방의 이전 메시지를 조회할 수 있어야 한다. | 필수 | `GET /chatrooms/{roomId}/messages`, `chat_messages` 커서 기반 페이지네이션 |
| FR-05-05 | 허가되지 않은 사용자는 해당 채팅방에 접근할 수 없어야 한다. | 필수 | STOMP 연결/구독 시 `ChannelInterceptor`에서 채팅방의 매칭 참여자 여부 검증 |
| FR-05-06 | 매칭 종료 이후 채팅방을 종료 상태로 전환할 수 있어야 한다. | 선택 | `PATCH /chatrooms/{roomId}/close`, `status = closed` 처리 후 메시지 전송 차단 |

## 공통 처리 원칙

| 항목 | 내용 |
| --- | --- |
| 인증 방식 | Spring Security가 이메일·비밀번호 및 카카오·Google OAuth2 로그인을 직접 처리한다. 계정당 하나의 가입 방식만 허용하고 동일 이메일의 다른 Provider 계정을 자동 연결하지 않는다. 서버가 환경변수로 관리하는 공통 비밀키와 HS256(HMAC-SHA256) 알고리즘으로 Access Token을 발급·검증하며, Refresh Token은 해시하여 DB에 저장하고 재발급 시 회전(RTR)시킨다. 사용자당 최대 활성 세션 수는 기본 5개로 제한(초과 시 가장 오래된 활성 family부터 LRU 폐기)하며, 만료된 토큰은 RTR 재사용 탐지 유예기간(7일) 보관 후 스케줄러(매일 04:00 KST)를 통해 자동 삭제된다. JWT 검증 시 허용 알고리즘을 HS256으로 제한하고 `iss`, `aud`, `exp` 클레임을 검증한다. |
| OAuth 가입 예외 | OAuth 이메일 없음·미검증은 가입 실패로 처리한다. 동일 이메일의 다른 Provider 가입은 자동 연결하지 않고 기존 방식을 안내한다. 닉네임이 없거나 중복되면 무작위 임시 닉네임을 생성하고 최초 토큰 교환 응답의 `profileSetupRequired`로 프로필 수정 화면 이동을 유도한다. |
| 성향 데이터 원칙 | 성향은 자가 응답 기반 식사·대화 선호로 한정하고 심리 진단이나 민감 특성을 추론하지 않는다. 온보딩은 건너뛸 수 있어야 하며 사용자가 결과를 조회·수정·초기화할 수 있어야 한다. 나의 성향과 원하는 상대의 중요도는 별도로 저장한다. |
| 임베딩 사용 원칙 | 필수 조건(위치/시간 등 명확한 값)은 항상 하드 필터로 처리하고, 벡터 유사도는 "성향/분위기/자유 텍스트"처럼 모호한 선호도를 다루는 보조 랭킹 수단으로만 사용한다. 성향 임베딩은 양쪽 자유 텍스트만 동일한 정규화·버전 계열(`PERSONALITY_FREE_TEXT_V2`)로 생성한다. 카드 점수와 태그는 임베딩에 중복 포함하지 않는다. 모델명·차원·소스 버전을 함께 관리하고 서로 다른 모델의 벡터를 직접 비교하지 않는다. |
| 장애 격리 | AI/임베딩 관련 기능은 모두 핵심 매칭·채팅 플로우와 분리하여, 실패 시에도 기본 기능은 영향받지 않도록 설계 |
| API 문서화 | Springdoc OpenAPI(Swagger)로 전 엔드포인트 자동 문서화 |
| 모니터링 | Prometheus + Grafana로 매칭 대기열 크기, 매칭 성사율, AI 응답 지연/실패율, WebSocket 연결 수 등 추적 |

### 매칭 메트릭

매칭 후보 제안 탐색 시도는 다음 Micrometer 메트릭으로 Prometheus에 노출한다. 태그에는 고정된 결과 값만 사용하며 사용자 ID, 요청 ID, 좌표와 같은 식별자·고카디널리티 값은 포함하지 않는다.

| 메트릭 | 태그 | 의미 |
| --- | --- | --- |
| `matching_requests_total` | `result=created\|no_candidate\|skipped\|retry_later` | 후보 제안 탐색 시도 결과별 누적 횟수 |
| `matching_duration_seconds` | `result=created\|no_candidate\|skipped\|retry_later` | 후보 제안 탐색 처리 시간. 히스토그램 버킷을 함께 노출해 p95 조회에 사용 |
| `matching_completed_total` | 없음 | 양쪽 사용자가 수락하고 최종 매칭 트랜잭션이 커밋된 누적 횟수 |
