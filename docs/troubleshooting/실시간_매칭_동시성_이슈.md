# [Troubleshooting] 사용자당 중복 실시간 매칭 요청 및 동시성 이슈

## 1. 증상 (Symptom)

- 사용자가 실시간 1:1 맛집 매칭 요청 시 버튼을 연타(빠른 연속 클릭)하거나 여러 탭/디바이스에서 동시 매칭을 요청할 때 중복 대기 요청(`MatchRequest`)이 생성됨.
- 비동기 후보 탐색 및 매칭 확정 과정에서 경쟁 조건(Race Condition)이 발생하여, **한 사용자가 동시에 2개 이상의 매칭(`Match.status = MATCHED`) 및 활성 채팅방에 매핑되는 현상** 발생.
- 데이터 정합성이 상실되고 한 유저가 두 명의 상대와 동시에 매칭되어 서비스 흐름이 파기되는 동시성 문제.

---

## 2. 원인 (Cause)

### ① 단순 SELECT 조회 기반 검사의 한계
- 기존 요청 생성 검사 로직은 단순히 `WAITING` 상태의 매칭 요청 존재 여부를 단순 SELECT로만 확인했음.
- 두 동시 요청이 거의 같은 시점에 진입하는 경우, 트랜잭션 A와 B가 모두 "기존 활성 대기 요청 없음"으로 판정하여 두 요청 모두 DB에 저장됨.

### ② 비동기 매칭 탐색 및 확정 시 경쟁 조건 (Race Condition)
- Redis 기반의 Geo 대기열 탐색과 PostgreSQL의 제안/매칭 저장 간 비동기 시차로 인해, 두 명의 후보가 동일 유저에게 동시에 상호 수락을 완료할 때 두 `Match` 행과 `ChatRoom`이 원자적 잠금 없이 각각 생성되는 현상이 가능했음.

---

## 3. 해결 (Solution)

### ① Redis 분산 원자적 잠금 (`SET NX`)
- 매칭 요청 생성 진입 시 Redis 키 `match:user:{userId}`를 `SET NX` (TTL 5분) 연산으로 생성.
- 동일 사용자의 추가 대기 요청이나 제안 수락 중 중복 진입을 원자적으로 차단하고 `409 Conflict` (`MATCHING_003`) 에러 반환.

```java
// Redis 원자적 세션 예약 예시
Boolean acquired = redisTemplate.opsForValue()
    .setIfAbsent("match:user:" + userId, requestId, Duration.ofMinutes(5));
if (Boolean.FALSE.equals(acquired)) {
    throw new DuplicateMatchRequestException("이미 진행 중인 매칭 요청이 존재합니다.");
}
```

### ② DB 트랜잭션 오름차순 비관적 잠금 (Pessimistic Locking)
- 상호 수락 및 최종 매칭(`matches`) 확정 트랜잭션 수행 시, 두 `MatchRequest` ID를 **작은 ID 순서(`request_1_id < request_2_id`)로 정렬하여 `PESSIMISTIC_WRITE` 잠금**을 획득.
- 정렬된 비관적 잠금을 통해 두 트랜잭션 간 교착 상태(Deadlock)를 방지하고, 경쟁 상황에서 한쪽 트랜잭션만 성공하고 나머지 요청은 차단 또는 대기 복귀하도록 처리.

### ③ 사용자당 활성 매칭 1개 정책 및 DB 검증
- 서비스 계층 및 스키마 수준에서 `MATCHED` 상태를 유일한 활성 매칭으로 정의.
- 새 매칭 요청 생성 전에 `Match.status = MATCHED`인 활성 매칭 존재 여부를 사전 조회하여 활성 매칭이 존재하는 경우 요청 생성을 차단(`409 Conflict`, `MATCHING_014`).

---

## 4. 성과 및 결론

- 분산 예약 키(`SET NX`)와 DB 오름차순 비관적 잠금을 통해 중복 매칭 요청 및 경쟁 조건 해결.
- 한 사용자에게 2개 이상의 활성 매칭/채팅방이 생성되지 않도록 데이터 정합성 보장.
