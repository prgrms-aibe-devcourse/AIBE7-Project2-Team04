# 후기 오남용·운영 검토 후속 TODO

> 현재 MVP는 실제 매칭 참여자 검증, 완료 매칭·작성 기간 검증, 중복 방지와 익명 집계만 제공한다. 계정 반복 생성·담합 평가의 자동 탐지와 관리자 제재는 후기 API와 분리된 운영 기능으로 다룬다.

## 운영 이벤트와 개인정보 최소화

- [x] 후기 제출·중복 거부·작성 기간 만료·신고 처리 이벤트를 감사 이벤트로 정의한다. (`ReviewAuditEvent.Type`)
- [x] 이벤트에는 원문 답변, JWT·Refresh Token, OAuth Provider ID, 이메일, 정밀 위치를 기록하지 않는다. 이벤트에는 고정 코드와 운영용 가명 키만 포함한다.
- [x] 계정·매칭·후기 식별자는 `REVIEW_AUDIT_PSEUDONYM_KEY` 기반 HMAC-SHA-256 가명 키로 기록하고, `REVIEW_AUDIT_PSEUDONYM_KEY_VERSION`으로 키 회전 시 버전을 구분한다. 원본과 결합 가능한 키는 Secret Manager에만 보관하고 운영·보안·개인정보 담당 권한으로 제한한다.
- [x] 후기 감사 이벤트에는 IP·User-Agent·디바이스 정보를 수집하지 않는다. 향후 수집이 필요하면 수집 목적·법적 근거·보관 기간·접근 주체·파기 절차를 개인정보 담당자 승인 후 별도 적용한다.
- [x] `audit.review` 전용 로그를 감사 로그로 분리하고 기술적 기본 보존 기간을 90일로 정한다. 운영 로그 플랫폼에서 조회 권한과 파기 정책을 적용하며, 일반 애플리케이션 로그에는 식별자 대신 집계 건수와 오류 코드만 남긴다.

> 구현 메모: 성공한 후기 제출 이벤트는 DB 커밋 이후에만 발행하고, 중복 거부·작성 기간 만료 이벤트는 요청 트랜잭션이 롤백되어도 운영 원인 추적을 위해 즉시 발행한다. 신고 처리 기능이 추가될 때 `ReviewAuditEventPublisher.reportHandled(...)`를 호출하며 신고 원문이나 처리자 원본 식별자는 이벤트에 전달하지 않는다. 운영 환경에서는 반드시 32바이트 이상의 `REVIEW_AUDIT_PSEUDONYM_KEY`를 Secret Manager에서 주입한다.

## 반복 생성·담합 평가 탐지

- [ ] 동일 기간 내 반복 가입, 동일 가명 키의 다계정 생성, 짧은 시간의 상호 평가, 동일 매칭군의 비정상 평가 집중을 탐지할 지표와 임계값을 정한다.
- [ ] 탐지 결과는 자동 제재가 아닌 관리자 검토 큐로 전달하고, 오탐 이의제기와 재검토 절차를 제공한다.
- [ ] 탐지 규칙을 변경할 때 기존 사용자에게 불리한 소급 제재가 발생하지 않는지 버전과 변경 이력을 남긴다.

## 신고·무효화·지수 연동

- [ ] 신고 승인, 운영상 무효화, 삭제 상태를 표현할 데이터 모델과 상태 전이를 확정한다.
- [ ] 상태 전이별로 공개 집계 포함 여부를 `PUBLIC`·유효 상태 조건으로 일관되게 적용하고, 변경 즉시 또는 재계산 작업으로 지수를 갱신한다.
- [ ] 무효화된 후기의 집계 제외와 복구 시 재포함을 검증하는 DB 호환 통합 테스트를 추가한다.

## 다시한끼 지수 산식 버전

- [ ] `ReviewScorePolicy.CURRENT_VERSION` 변경 전 기존 버전과 새 버전의 사용자별 점수를 비교한다.
- [ ] 점수 하락 사용자, 최소 표본 경계(2↔3건), 반올림 경계의 영향과 안내 문구를 검토한 뒤 새 버전을 배포한다.
- [ ] 필요하면 버전별 재계산 결과를 별도 감사 저장소에 보관하되 외부 응답에는 산식 버전을 노출하지 않는다.
