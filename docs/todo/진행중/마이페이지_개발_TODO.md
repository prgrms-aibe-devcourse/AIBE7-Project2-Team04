# 마이페이지 개발 TODO

> 로그인 사용자가 자신의 프로필과 성향 설정을 관리하고, 참여한 매칭 이력과 받은 후기를 안전하게 조회할 수 있는 마이페이지를 구현한다. 기존 회원·성향·매칭·후기 도메인의 책임을 재사용하며, 마이페이지라는 이유로 서로 무관한 조회와 수정 로직을 하나의 컨트롤러나 서비스에 모으지 않는다.

## 목표

- 자신의 프로필을 조회·수정하고 성향 및 음식 선호 설정 화면으로 이동할 수 있게 한다.
- 자신이 실제 참여한 매칭 이력과 받은 후기만 최신순으로 조회할 수 있게 한다.
- 프로필, 매칭, 후기별 로딩·빈 상태·오류 상태를 독립적으로 처리한다.
- JWT의 사용자 ID를 기준으로 본인 데이터만 반환하고 민감 정보와 내부 매칭 데이터를 노출하지 않는다.
- 기존 API와 도메인 로직을 재사용하고 중복 엔드포인트·N+1 조회·무제한 목록 응답을 만들지 않는다.

- [ ] 잘못된 페이지 크기·정렬 값은 제한하거나 `400` 한국어 검증 메시지로 응답한다.

## 7. 마이페이지 프론트엔드 구조

- [ ] 인증 사용자만 접근 가능한 `/mypage` 라우트와 공통 헤더의 마이페이지 진입점을 추가한다.
- [ ] 비인증 접근 시 로그인 화면으로 이동시키되 원래 이동하려던 경로를 안전하게 복원한다.
- [ ] 프로필, 매칭 이력, 받은 후기를 탭 또는 구획으로 나누고 모바일·데스크톱 레이아웃을 정의한다.
- [ ] 영역별 API 모듈을 분리하고 공통 `credentials: 'include'`, CSRF, 오류 파싱 규칙을 재사용한다.
- [ ] 초기 로딩 스켈레톤, 빈 상태, 재시도 가능한 오류를 프로필·매칭·후기별로 독립 표시한다.
- [ ] 한 영역의 실패가 다른 영역의 정상 데이터 표시를 막지 않도록 병렬 호출 결과를 격리한다.
- [ ] 키보드 탐색, 포커스 표시, 시맨틱 제목 구조, 폼 레이블과 상태 안내의 스크린리더 전달을 지원한다.
- [ ] 작은 화면에서 긴 닉네임·소개·후기 내용과 많은 이력이 레이아웃을 깨뜨리지 않게 한다.

- [ ] 수정 폼에 서버와 동일한 길이·형식 검증을 적용하되 서버 검증을 최종 기준으로 유지한다.
- [ ] 저장 중 중복 제출을 막고 성공 시 응답값으로 화면과 공통 헤더 닉네임을 갱신한다.
- [ ] 닉네임 중복, 이미지 업로드 실패, 세션 만료, CSRF 실패를 구분한 한국어 안내를 제공한다.
- [ ] 프로필 이미지가 없거나 로드에 실패하면 접근 가능한 기본 이미지를 표시한다.
- [ ] 성향 상태에 따라 `설문 시작`, `다시 작성`, `초기화` 진입점을 기존 `/personality/survey` 흐름에 연결한다.
- [ ] 음식 선호 편집은 기존 API를 재사용하고 프로필 PATCH와 중복 저장하지 않는다.
- [ ] OAuth 최초 로그인 사용자의 `/profile/setup` 임시 화면을 실제 수정 폼과 통합하거나 같은 컴포넌트를 재사용한다.

## 9. 매칭 이력·후기 프론트엔드

- [ ] 매칭 이력에 상대방 공개 프로필, 상태, 매칭 시각, 종료 시각과 가능한 후속 행동을 표시한다.
- [ ] 활성 매칭은 채팅방으로 이동할 수 있게 하고 종료된 매칭은 상태에 맞는 읽기 전용 표현을 사용한다.
- [ ] 이력의 상태 코드를 `진행 중`, `완료`, `취소됨` 등 사용자용 한국어로 매핑한다.
- [ ] 받은 후기에는 작성자 공개 프로필, 별점, 작성 시각, 내용과 공개 범위를 정책에 맞게 표시한다.
- [ ] 후기 내용은 HTML로 주입하지 않고 텍스트로 렌더링해 XSS를 방지한다.
- [ ] 목록 추가 로드 또는 페이지 이동 중 중복 요청을 막고 마지막 페이지·빈 결과를 올바르게 처리한다.
- [ ] 삭제·비공개 전환·신고 버튼은 해당 API와 정책이 구현되기 전 노출하지 않는다.

## 10. 계정과 보안

- [ ] 로그아웃 버튼은 기존 `/auth/logout`을 호출해 Refresh Token을 폐기한 뒤 클라이언트 인증 상태를 정리한다.
- [ ] 회원탈퇴를 포함하는 경우 확인 절차, 재인증 필요 여부, `users.status = WITHDRAWN`, 개인정보 마스킹과 전체 Refresh Token 폐기를 하나의 정책으로 구현한다.
- [ ] LOCAL, KAKAO, GOOGLE 계정을 자동 연결하거나 Provider 자체 로그아웃·연결 해제로 오인되는 동작을 추가하지 않는다.
- [ ] 상태 변경 요청은 기존 쿠키 기반 CSRF 보호와 `X-XSRF-TOKEN` 헤더 규칙을 유지한다.
- [ ] CORS Origin을 넓히거나 Access Token·Refresh Token을 URL 또는 로그에 기록하지 않는다.
- [ ] 조회 응답·오류 메시지·서버 로그에 비밀번호 해시, 토큰, Provider ID, 성향 원본·임베딩, 정밀 위치가 남지 않는지 점검한다.
- [ ] 타인의 매칭 ID·후기 ID를 추측해도 데이터 존재 여부나 비공개 정보가 노출되지 않게 한다.

## 11. 백엔드 테스트

- [ ] 인증 사용자만 프로필·매칭 이력·후기 조회가 가능하고 비인증 요청은 `401`인지 테스트한다.
- [ ] 프로필 조회가 허용 필드만 반환하고 민감 필드를 제외하는지 컨트롤러 테스트를 작성한다.
- [ ] 프로필 PATCH의 부분 수정, 필드 삭제, 검증 실패와 닉네임 중복 경쟁을 테스트한다.
- [ ] 탈퇴·미존재 사용자의 조회와 수정이 공통 한국어 오류로 처리되는지 테스트한다.
- [ ] 매칭 이력이 본인 참여 건만 최신순으로 반환되고 타인의 매칭은 제외되는지 테스트한다.
- [ ] 매칭 이력 응답에서 상대방 공개 필드만 포함되고 정밀 핀·내부 성향 데이터가 제외되는지 테스트한다.
- [ ] 받은 후기만 최신순으로 반환되고 작성한 후기나 타인의 후기가 섞이지 않는지 테스트한다.
- [ ] 공개·비공개 후기, 탈퇴 작성자, 내용 없는 후기 정책을 테스트한다.
- [ ] 페이지 경계, 최대 크기 제한, 동일 시각 동률 정렬과 빈 페이지를 테스트한다.
- [ ] 필요한 연관 조회에서 N+1이 발생하지 않는지 통합 테스트 또는 쿼리 수 검증을 추가한다.
- [ ] Repository 테스트는 PostgreSQL 전용 매핑과 실제 쿼리 호환성을 고려해 수행한다.

## 12. 프론트엔드 검증

- [ ] 세션 만료 시 각 API의 반복 실패를 만들지 않고 로그인 안내로 전환되는지 확인한다.
- [ ] 프로필 수정 성공·검증 실패·닉네임 충돌·이미지 실패 시 폼 상태와 안내가 정확한지 확인한다.
- [ ] 성향 미시작·건너뜀·완료 상태별 진입 버튼과 설문 복귀가 정상 동작하는지 확인한다.
- [ ] 매칭·후기 0건, 1건, 여러 페이지와 느린 네트워크 상태를 확인한다.
- [ ] 한 API만 실패했을 때 나머지 마이페이지 영역을 계속 사용할 수 있는지 확인한다.
- [ ] 긴 한국어·영문·이모지 입력, 깨진 이미지와 모바일 화면을 확인한다.
- [ ] 키보드만으로 탭, 수정 폼, 페이지 이동과 로그아웃을 사용할 수 있는지 확인한다.
- [ ] 변경된 JavaScript 파일 문법 검사와 `npm.cmd run build`를 통과한다.

## 완료 기준

- [ ] 로그인 사용자가 마이페이지에서 자신의 최신 프로필을 조회·수정하고 성향·음식 선호 설정으로 이동할 수 있다.
- [ ] 사용자가 자신이 참여한 매칭 이력과 받은 후기를 안정적인 최신순 페이지로 조회할 수 있다.
- [ ] 모든 조회·수정은 인증 사용자 본인 범위로 제한되고 민감 정보·정밀 위치·내부 성향 데이터가 노출되지 않는다.
- [ ] 프로필, 매칭 이력, 받은 후기의 컨트롤러·서비스·DTO 책임이 도메인별로 분리되어 있다.
- [ ] 모바일·데스크톱에서 로딩·빈 상태·부분 실패·세션 만료와 접근성 흐름이 검증된다.
- [ ] 관련 자동 테스트, Java 컴파일·테스트, 프론트 빌드와 소스 오브 트루스 문서 동기화가 모두 완료된다.
