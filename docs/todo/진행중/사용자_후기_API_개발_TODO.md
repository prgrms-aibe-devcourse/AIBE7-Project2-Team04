# 사용자 후기 API 및 다시한끼 지수 개발 TODO

> 실제 매칭에 참여한 사용자가 상대방에 대한 재만남 의향을 간단히 남기고, 받은 평가를 기반으로 사용자의 `다시한끼` 지수와 인상 태그 요약을 제공한다. 후기 도메인이 작성·조회·집계 규칙을 소유하고, 마이페이지는 후기 조회 API를 호출해 결과를 표시한다.

## 목표

- 필수 질문 하나와 선택 태그 최대 하나만으로 부담 없이 후기를 제출할 수 있게 한다.
- 인증 사용자와 실제 매칭 참여 관계를 검증해 본인이 만난 상대에게만 후기를 작성할 수 있게 한다.
- 동일 매칭·동일 상대에 대한 중복 후기를 차단한다.
- 받은 재만남 의향을 안정적으로 집계해 `다시한끼` 지수로 표현한다.
- 선택 태그는 긍정적인 인상 요약으로 제공하되, 태그를 생략한 사용자가 점수상 불이익을 받지 않게 한다.
- 후기 작성 API와 받은 후기·지수 조회 API는 `review` 도메인이 담당하고, 마이페이지는 API 소비와 화면 표시만 담당한다.

## 확정된 제품 규칙

- [x] 필수 질문은 `이 사용자와 또 만나고 싶나요?` 한 문항이다.
- [x] 필수 답변은 `꼭 또 보고 싶어요`, `기회가 되면 좋아요`, `이번 만남으로 충분해요` 중 정확히 하나다.
- [x] 필수 답변 하나만 선택하면 태그 없이도 제출할 수 있다.
- [x] 선택 질문은 `가장 인상 깊었던 점은 무엇인가요?`이다.
- [x] 선택 태그는 `시간 약속`, `편안한 대화`, `배려`, `적극적인 참여` 중 최대 하나다.
- [x] MVP 후기 작성 입력에는 별점과 자유 서술형 내용을 요구하지 않는다.
- [x] 사용자 평가 집계의 서비스 명칭은 `다시한끼` 지수로 사용한다.

## 1. 구현 전 정책 확정

- [x] 후기 작성 가능 시점을 별도 만남 완료 처리로 확정한다.
- [x] 후기 작성 가능 기간은 서버에 기록된 매칭 완료 시점부터 7일로 한다.
- [x] 작성 가능 범위는 `completedAt <= now < completedAt + 7일`로 한다.
- [x] 기한이 지난 미작성 후기 요청은 `410 REVIEW_PERIOD_EXPIRED`와 한국어 안내 메시지로 처리한다.
- [x] 마이페이지 매칭 이력에 `reviewStatus`와 `reviewDeadlineAt`을 제공한다.
- [x] 매칭 참여자 두 명이 각각 상대에게 한 번씩 작성할 수 있는 정책을 확정한다.
- [x] 후기 작성 후 수정·삭제를 허용하지 않는다.
- [x] 상대방이 작성한 개별 재만남 의향을 수신자에게 그대로 보여 주는 것으로 확정한다.
- [x] 부정적 선택으로 작성자를 추론하거나 보복하는 일을 줄이기 위해 원본 답변 대신 집계 결과만 노출하는 것으로 확정한다.
- [x] MVP에서는 개별 후기와 선택 태그 통계를 사용자에게 노출하지 않고 다시한끼 지수만 제공한다.
- [x] 선택 태그는 내부 통계와 향후 긍정 배지 기능을 위해 저장한다.
- [x] 태그를 선택하지 않아도 다시한끼 지수 계산에서 불이익을 주지 않는다.
- [x] 향후 태그 통계를 공개할 때 최소 표본 수와 익명성 정책을 별도로 정의한다.
- [x] 후기 작성자는 `ACTIVE` 상태의 인증 사용자만 허용한다.
- [x] 평가 대상이 `ACTIVE` 상태일 때만 새 후기를 작성할 수 있다.
- [x] 작성자 또는 평가 대상이 `WITHDRAWN` 상태이면 새 후기 작성을 허용하지 않는다.
- [x] 후기 작성자가 이후 탈퇴해도 기존 후기는 자동 삭제하거나 집계에서 제외하지 않는다.
- [x] 탈퇴 작성자의 공개 프로필 정보는 익명화하고 기존 후기의 집계 결과만 유지한다.
- [x] 평가 대상이 탈퇴하면 다시한끼 지수와 후기 요약을 외부에 노출하지 않는다.
- [x] `다시한끼` 지수를 매칭 후보 정렬이나 노출 제한에 사용할지는 MVP 범위에서 제외하고 별도 정책으로 관리한다.

- [x] 재만남 의향 Enum의 내부 이름과 고정 API 값을 `DEFINITELY_AGAIN`, `MAYBE_AGAIN`, `ENOUGH_FOR_NOW`로 확정했다.
- [x] 재만남 의향의 한국어 표시 문구는 Enum의 label로 분리하고 API 응답은 고정 코드만 전달한다.
- [x] 인상 태그 Enum의 내부 이름과 고정 API 값을 `PUNCTUAL`, `COMFORTABLE_CONVERSATION`, `CONSIDERATE`, `ACTIVE_PARTICIPATION`로 확정했다.
- [x] 인상 태그의 한국어 표시 문구는 Enum의 label로 분리하고 API 응답은 고정 코드만 전달한다.

- [ ] 필수 재만남 의향 누락과 복수 태그 입력의 한국어 HTTP 응답은 후기 요청 DTO·컨트롤러와 함께 구현한다(5·8번 범위).

## 5. 후기 작성 API 계약

- [ ] 기존 명세와의 호환성을 고려해 `POST /reviews`를 최종 작성 경로로 확정한다.
- [ ] 요청 DTO는 `matchId`, `revisitIntention`, nullable `impressionTag`만 받는 것을 우선안으로 한다.
- [ ] `reviewerId`는 JWT 인증 정보에서 가져오고 요청 본문에서 받지 않는다.
- [ ] 1:1 매칭의 상대방은 `matchId`와 인증 사용자 참여 정보로 서버에서 결정하고 `targetUserId`를 신뢰하지 않는다.
- [ ] 성공 상태를 `201 Created`로 할지 확정하고 생성된 후기 ID, 제출 시각과 갱신된 요약 중 필요한 최소 필드만 반환한다.
- [ ] 중복 제출은 Unique 제약과 서비스 사전 검증을 함께 사용해 `409`와 한국어 오류 메시지로 처리한다.
- [ ] 미인증은 `401`, 실제 참여자가 아니거나 작성 대상이 아니면 `403`, 매칭 없음은 정보 노출을 고려해 `404`로 처리한다.
- [ ] 작성 가능 상태·기한이 아니면 별도 오류 코드를 정의하고 사용자 행동을 안내하는 한국어 메시지를 반환한다.
- [ ] 쿠키 기반 인증 흐름의 상태 변경 요청이므로 기존 CSRF 토큰과 `X-XSRF-TOKEN` 헤더 규칙을 유지한다.
- [ ] 네트워크 재시도로 동일 요청이 반복될 때 중복 레코드가 생기지 않도록 멱등성 또는 Unique 충돌 응답 정책을 문서화한다.

### 요청 예시 검토안

```json
{
  "matchId": 301,
  "revisitIntention": "DEFINITELY_AGAIN",
  "impressionTag": "PUNCTUAL"
}
```

태그를 선택하지 않은 경우:

```json
{
  "matchId": 301,
  "revisitIntention": "MAYBE_AGAIN",
  "impressionTag": null
}
```

## 6. 받은 후기·다시한끼 조회 API 계약

- [ ] `GET /mypage/reviews`가 인증 사용자의 받은 후기와 다시한끼 요약을 반환하는 최종 계약인지 확정한다.
- [ ] `GET /users/{userId}/reviews`는 공개 프로필용 집계만 반환할지, 공개 가능한 개별 후기 목록도 반환할지 확정한다.
- [ ] 마이페이지 응답에 `dasiHankkiScore`, 유효 후기 수, 태그별 횟수·비율과 최근 후기 페이지 중 필요한 값을 정의한다.
- [ ] 개별 재만남 의향을 숨기는 정책이면 응답 DTO와 Repository Projection에서 해당 값을 제외한다.
- [ ] 작성자 UUID, 이메일, OAuth Provider 식별자와 매칭의 정밀 위치·성향 내부 데이터를 노출하지 않는다.
- [ ] 태그 통계는 고정된 표시 순서로 반환하고 0건 태그의 포함 여부를 확정한다.
- [ ] 후기 0건은 오류가 아닌 `200`으로 반환하고 지수 값 또는 `아직 후기가 없어요` 상태 표현을 계약에 포함한다.
- [ ] 목록을 제공한다면 기본 정렬을 `createdAt DESC, id DESC`로 고정하고 페이지 크기 상한을 적용한다.
- [ ] 공개 프로필과 본인 마이페이지의 노출 필드를 별도 DTO와 조회 메서드로 분리한다.
- [ ] 지수 산식 버전과 마지막 계산 시각을 외부 응답에 노출할 필요가 있는지 확정한다.

## 7. 데이터 모델 및 마이그레이션

- [ ] 기존 `user_reviews.rating`, `content` 구조를 새 정책과 비교하고 운영 데이터 존재 여부를 확인한다.
- [ ] `revisit_intention VARCHAR(...) NOT NULL` 컬럼과 nullable `impression_tag VARCHAR(...)` 컬럼을 추가한다.
- [ ] 기존 데이터가 있다면 컬럼 추가, 데이터 변환·백필, NOT NULL 적용을 단계적으로 수행한다.
- [ ] 기존 `rating`과 `content`는 즉시 파괴적으로 삭제하지 않고 API 전환과 데이터 검증 후 제거 여부를 결정한다.
- [ ] `(match_id, reviewer_id, reviewee_id)` Unique 제약을 유지한다.
- [ ] 작성자와 대상자가 다르다는 Check 제약과 허용 Enum 값 Check 제약을 DB에도 적용할지 결정한다.
- [ ] 받은 후기 최신순 조회를 위한 `(reviewee_id, created_at DESC, id DESC)` 인덱스를 검토한다.
- [ ] 공개 후기 조회가 필요하면 공개 범위와 대상 사용자 기준의 복합 인덱스를 검토한다.
- [ ] 다시한끼 지수의 원본은 후기 레코드로 유지하고, 파생 점수만 재계산 가능하게 설계한다.
- [ ] MVP는 집계 쿼리로 계산할지, `user_review_summaries` 같은 요약 테이블을 둘지 예상 트래픽과 일관성 요구로 결정한다.
- [ ] 요약 테이블을 사용하면 후기 저장과 집계 갱신을 같은 트랜잭션에서 처리하고 전체 재계산 절차를 제공한다.
- [ ] Entity 관계는 기본 LAZY로 두고 API 응답에 Entity를 직접 노출하지 않는다.
- [ ] 비파괴적 마이그레이션 SQL과 롤백·검증 절차를 `docs/migrations/`에 추가한다.

## 8. 백엔드 구현

- [ ] `review/controller`, `service`, `repository`, `entity`, `dto` 구조를 유지한다.
- [ ] 후기 작성 Service에 트랜잭션 경계를 두고 참여자 검증, 대상자 결정, 중복 검증, 저장과 집계 갱신을 처리한다.
- [ ] 매칭 상태와 참여자 검증은 기존 matching 도메인의 공개 Service를 재사용하고 내부 Repository를 중복 구현하지 않는다.
- [ ] `matchId`로 정확히 두 명의 참여자가 확인되지 않는 비정상 데이터는 저장하지 않고 관측 가능한 오류로 처리한다.
- [ ] Controller는 인증 사용자 식별과 DTO 검증·응답 변환만 담당한다.
- [ ] 받은 후기 조회 Service는 `@Transactional(readOnly = true)`를 사용한다.
- [ ] 지수와 태그 통계 집계에서 N+1 조회가 발생하지 않도록 집계 쿼리 또는 Projection을 사용한다.
- [ ] DB Unique 충돌을 공통 예외로 변환하고 SQL·내부 Entity 정보가 응답에 노출되지 않게 한다.
- [ ] 애플리케이션 오류와 Bean Validation 메시지는 한국어로 작성한다.
- [ ] 로그에 후기 원문 전체, JWT, OAuth 식별자나 정밀 위치 정보를 남기지 않는다.

## 9. 오남용·개인정보·공정성

- [ ] 타인의 `matchId`를 추측해도 참여 여부와 상대 사용자 정보를 알아낼 수 없게 한다.
- [ ] 자기 자신을 대상으로 후기를 작성할 수 없게 서비스와 DB에서 모두 차단한다.
- [ ] 취소된 매칭을 이용한 후기 작성과 한 사용자의 중복 제출을 차단한다.
- [ ] 지수 계산에서 비공개, 삭제, 신고 승인, 운영상 무효 처리된 후기의 포함 여부를 일관되게 적용한다.
- [ ] 작성자 익명화 여부와 최소 표본 수를 적용해 단일 후기의 작성자를 추론하기 어렵게 한다.
- [ ] 다시한끼 지수를 사람의 안전성·신뢰성을 보증하는 절대 척도로 표현하지 않고 참고 지표임을 안내한다.
- [ ] 계정 생성 반복이나 담합 평가를 탐지할 운영 로그·관리자 검토 범위를 별도 후속 작업으로 정의한다.
- [ ] 지수 산식 변경 시 기존 사용자에게 불리한 소급 변경이 발생하는지 검토하고 버전별 재계산 결과를 확인한다.

## 10. 백엔드 테스트

- [ ] 인증된 실제 참여자가 유효한 필수 답변만으로 후기를 작성할 수 있는지 테스트한다.
- [ ] 네 가지 선택 태그 각각과 태그 미선택 제출을 테스트한다.
- [ ] 필수 답변 누락, 알 수 없는 답변·태그와 잘못된 JSON에 `400`과 한국어 메시지가 반환되는지 테스트한다.
- [ ] 미인증, 비참여자, 자기 자신 대상, 작성 불가 매칭 상태와 작성 기한 만료를 테스트한다.
- [ ] 동일 매칭·작성자·대상자 중복 제출이 경쟁 상황에서도 하나만 저장되고 나머지는 `409`인지 테스트한다.
- [ ] 두 참여자가 서로에게 각각 한 번씩 작성할 수 있는지 테스트한다.
- [ ] 다시한끼 지수의 후기 0건·1건·여러 건, 세 답변 조합, 반올림과 경계값을 단위 테스트한다.
- [ ] 태그 미선택이 지수에 영향을 주지 않고 태그 통계에서만 제외되는지 테스트한다.
- [ ] 후기 무효화·수정·삭제 정책에 따라 지수와 태그 통계가 재계산되는지 테스트한다.
- [ ] 받은 후기 조회가 본인 데이터만 반환하고 타인의 후기·작성한 후기가 섞이지 않는지 테스트한다.
- [ ] 공개 조회에서 비공개 원본 답변, 작성자 식별자와 민감 데이터가 제외되는지 테스트한다.
- [ ] 동일 시각 데이터의 정렬, 페이지 경계, 최대 페이지 크기와 빈 목록을 테스트한다.
- [ ] PostgreSQL Enum 문자열, Check·Unique 제약과 집계 쿼리를 실제 DB 호환 환경에서 검증한다.
- [ ] Hibernate 로그에 `CommandAcceptanceException`과 스키마 생성 오류가 없는지 확인한다.

## 11. 마이페이지 연동 체크

- [ ] 후기 팀이 확정 요청·응답 JSON, Enum 코드, 오류 코드와 Mock 응답을 마이페이지 팀에 제공한다.
- [ ] 마이페이지는 다시한끼 지수, 유효 후기 수와 상위 인상 태그를 별도 요약 영역에 표시한다.
- [ ] 최소 표본 미달이면 숫자 대신 `후기가 더 모이면 다시한끼 지수가 공개돼요` 같은 상태를 표시한다.
- [ ] 받은 후기 0건, 태그 0건, 일부 필드 비공개와 조회 오류 상태를 각각 처리한다.
- [ ] raw Enum을 그대로 노출하지 않고 확정된 한국어 문구로 매핑한다.
- [ ] 한 API 실패가 프로필·매칭 이력 등 다른 마이페이지 영역을 가리지 않게 한다.
- [ ] 지수와 태그를 HTML로 주입하지 않고 안전한 텍스트로 렌더링한다.
- [ ] 모바일·데스크톱, 긴 닉네임, 큰 후기 수와 소수점 표시를 확인한다.
