# 사용자 후기 API 및 다시한끼 지수 개발 TODO

> 실제 매칭에 참여한 사용자가 상대방에 대한 재만남 의향을 간단히 남기고, 받은 평가를 기반으로 사용자의 `다시한끼` 지수와 인상 태그 요약을 제공한다. 후기 도메인이 작성·조회·집계 규칙을 소유하고, 마이페이지는 후기 조회 API를 호출해 결과를 표시한다.

## 목표

- 필수 질문 하나와 선택 태그 최대 하나만으로 부담 없이 후기를 제출할 수 있게 한다.
- 인증 사용자와 실제 매칭 참여 관계를 검증해 본인이 만난 상대에게만 후기를 작성할 수 있게 한다.
- 동일 매칭·동일 상대에 대한 중복 후기를 차단한다.
- 받은 재만남 의향을 안정적으로 집계해 `다시한끼` 지수로 표현한다.
- 선택 태그는 긍정적인 인상 요약으로 제공하되, 태그를 생략한 사용자가 점수상 불이익을 받지 않게 한다.
- 후기 작성 API와 받은 후기·지수 조회 API는 `review` 도메인이 담당하고, 마이페이지는 API 소비와 화면 표시만 담당한다.

## 확정된 제품 규칙

- [x] 필수 질문은 `이 사용자와 또 만나고 싶나요?` 한 문항이다.
- [x] 필수 답변은 `꼭 또 보고 싶어요`, `기회가 되면 좋아요`, `이번 만남으로 충분해요` 중 정확히 하나다.
- [x] 필수 답변 하나만 선택하면 태그 없이도 제출할 수 있다.
- [x] 선택 질문은 `가장 인상 깊었던 점은 무엇인가요?`이다.
- [x] 선택 태그는 `시간 약속`, `편안한 대화`, `배려`, `적극적인 참여` 중 최대 하나다.
- [x] MVP 후기 작성 입력에는 별점과 자유 서술형 내용을 요구하지 않는다.
- [x] 사용자 평가 집계의 서비스 명칭은 `다시한끼` 지수로 사용한다.

## 1. 구현 전 정책 확정

- [x] 후기 작성 가능 시점을 별도 만남 완료 처리로 확정한다.
- [x] 후기 작성 가능 기간은 `matches.status = COMPLETED` 전환 시 서버에 기록된 `matches.ended_at`부터 7일로 한다.
- [x] 작성 가능 범위는 `ended_at <= now < ended_at + 7일`로 한다.
- [x] 기한이 지난 미작성 후기 요청은 `410 REVIEW_PERIOD_EXPIRED`와 한국어 안내 메시지로 처리한다.
- [x] 마이페이지 매칭 이력에 `reviewStatus`와 `reviewDeadlineAt`을 제공한다.
- [x] 매칭 참여자 두 명이 각각 상대에게 한 번씩 작성할 수 있는 정책을 확정한다.
- [x] 후기 작성 후 수정·삭제를 허용하지 않는다.
- [x] 상대방이 작성한 개별 재만남 의향은 수신자에게 그대로 보여 주지 않는 것으로 확정한다.
- [x] 부정적 선택으로 작성자를 추론하거나 보복하는 일을 줄이기 위해 원본 답변 대신 집계 결과만 노출하는 것으로 확정한다.
- [x] MVP에서는 개별 후기와 선택 태그 통계를 사용자에게 노출하지 않고 다시한끼 지수만 제공한다.
- [x] 선택 태그는 내부 통계와 향후 긍정 배지 기능을 위해 저장한다.
- [x] 태그를 선택하지 않아도 다시한끼 지수 계산에서 불이익을 주지 않는다.
- [x] 향후 태그 통계를 공개할 때 최소 표본 수와 익명성 정책을 별도로 정의한다.
- [x] 후기 작성자는 `ACTIVE` 상태의 인증 사용자만 허용한다.
- [x] 평가 대상이 `ACTIVE` 상태일 때만 새 후기를 작성할 수 있다.
- [x] 작성자 또는 평가 대상이 `WITHDRAWN` 상태이면 새 후기 작성을 허용하지 않는다.
- [x] 후기 작성자가 이후 탈퇴해도 기존 후기는 자동 삭제하거나 집계에서 제외하지 않는다.
- [x] 탈퇴 작성자의 공개 프로필 정보는 익명화하고 기존 후기의 집계 결과만 유지한다.
- [x] 평가 대상이 탈퇴하면 다시한끼 지수와 후기 요약을 외부에 노출하지 않는다.
- [x] `다시한끼` 지수를 매칭 후보 정렬이나 노출 제한에 사용할지는 MVP 범위에서 제외하고 별도 정책으로 관리한다.

- [x] 재만남 의향의 한국어 표시 문구는 Enum의 label로 분리하고 API 응답은 고정 코드만 전달한다.
- [x] 인상 태그 Enum의 내부 이름과 고정 API 값을 `PUNCTUAL`, `COMFORTABLE_CONVERSATION`, `CONSIDERATE`, `ACTIVE_PARTICIPATION`로 확정했다.
- [x] 인상 태그의 한국어 표시 문구는 Enum의 label로 분리하고 API 응답은 고정 코드만 전달한다.

## 5. 후기 작성 API 계약

- [x] 기존 명세와의 호환성을 고려해 `POST /reviews`를 최종 작성 경로로 확정했다.
- [x] 요청 DTO는 `matchId`, `revisitIntention`, nullable 단일 `impressionTag`만 받는다. `rating`, `content`, `targetUserId`, `reviewerId`는 포함하지 않는다.
- [x] `reviewerId`는 JWT 인증 정보에서 가져오고 요청 본문에서 받지 않는다.
- [x] 1:1 매칭의 상대방은 `matchId`와 인증 사용자 참여 정보로 서버에서 결정하고 `targetUserId`를 신뢰하지 않는다.
- [x] 성공 상태는 `201 Created`로 하고 `reviewId` 및 `submittedAt`만 반환한다. 갱신 요약은 작성 성공 응답에 포함하지 않는다.
- [x] 중복 제출은 서비스 사전 검증과 `(match_id, reviewer_id, reviewee_id)` Unique 제약을 함께 사용하고 `409 REVIEW_ALREADY_SUBMITTED`와 한국어 메시지로 처리한다.
- [x] 미인증은 `401 AUTH_001`, 작성자·평가 대상이 비활성 상태이거나 비정상 참여자 데이터이면 `403 AUTH_002`로 처리한다. 존재하지 않는 매칭과 비참여자가 추측한 매칭은 `404 COMMON_001`로 일반화해 정보 노출을 막는다.
- [x] 아직 완료되지 않은 매칭은 `409 REVIEW_NOT_AVAILABLE`, 7일 기한 만료는 `410 REVIEW_PERIOD_EXPIRED`로 구분하고 행동을 안내하는 한국어 메시지를 사용한다.
- [x] 쿠키 기반 인증 흐름의 상태 변경 요청이므로 기존 CSRF 토큰과 `X-XSRF-TOKEN` 헤더 규칙을 유지한다.
- [x] 네트워크 재시도로 동일 요청이 반복되면 서비스 사전 조회와 DB Unique 충돌을 함께 사용하고 `409 REVIEW_ALREADY_SUBMITTED`로 반환한다. 별도 `Idempotency-Key`는 요구하지 않는다.

### 요청 예시 검토안

```json
{
  "matchId": 301,
  "revisitIntention": "DEFINITELY_AGAIN",
  "impressionTag": "PUNCTUAL"
}
```

태그를 선택하지 않은 경우:

```json
{
  "matchId": 301,
  "revisitIntention": "MAYBE_AGAIN",
  "impressionTag": null
}
```

## 6. 받은 후기·다시한끼 조회 API 계약

- [x] `GET /mypage/reviews`는 인증 사용자의 받은 후기 집계와 다시한끼 요약만 반환하는 최종 계약으로 확정했다. MVP 개별 후기·원본 답변·태그 통계는 반환하지 않는다.
- [x] `GET /users/{userId}/reviews`는 공개 프로필용 집계만 반환하고 공개 가능한 개별 후기 목록은 MVP에서 제공하지 않는다.
- [x] 마이페이지 응답 필드는 `scoreStatus`, nullable `dasiHankkiScore`, `validReviewCount`로 확정했다. 태그별 횟수·비율과 최근 후기 페이지는 MVP에서 제외한다.
- [x] 개별 재만남 의향을 숨기는 정책에 따라 본인·공개 프로필 응답 DTO와 Repository Projection 계약에서 해당 값을 제외한다. 실제 Projection 구현은 8번에서 적용한다.
- [x] 작성자 UUID, 이메일, OAuth Provider 식별자와 매칭의 정밀 위치·성향 내부 데이터는 본인·공개 조회 응답에 포함하지 않는다.
- [x] 태그 통계는 MVP 외부 응답에서 제외한다. 향후 공개할 경우 네 가지 태그를 고정 순서로 반환하고 0건 태그도 포함한다.
- [x] 후기 0건과 3건 미만은 오류가 아닌 `200`으로 반환한다. 각각 `NO_REVIEWS`·`INSUFFICIENT_REVIEWS` 상태와 `아직 후기가 없어요`·`후기가 더 모이면 다시한끼 지수가 공개돼요` 표시를 사용한다.
- [x] 개별 목록은 MVP에서 제공하지 않아 페이지 파라미터를 받지 않는다. 향후 목록을 제공하면 `createdAt DESC, id DESC` 정렬과 `size` 최대 20을 적용한다.
- [x] 공개 프로필과 본인 마이페이지의 노출 필드를 별도 DTO와 조회 메서드 경계로 분리한다. 실제 Service·Repository 구현은 8번에서 적용한다.
- [x] 지수 산식 버전과 마지막 계산 시각은 MVP 외부 응답에 노출하지 않고 서버 내부 재계산·감사 정보로만 관리한다.

## 7. 데이터 모델 및 마이그레이션

- [x] 기존 `user_reviews.rating`, `content`는 새 정책에서 사용하지 않으므로 제거 대상으로 확정했다. 두 컬럼의 값이 없는지 확인하는 사전 검증을 마이그레이션에 포함했다.
- [x] `revisit_intention VARCHAR(30) NOT NULL`과 nullable `impression_tag VARCHAR(30)` 컬럼을 추가하는 것으로 확정했다.
- [x] 기존 `rating`·`content`는 의미가 다른 값으로 자동 백필하지 않으며, 값이 하나라도 남아 있으면 컬럼 삭제를 중단한다.
- [x] 백업과 사전 검증 후 `rating`·`content`를 명시적으로 DROP하고, 삭제 뒤 구버전 애플리케이션으로의 즉시 롤백은 지원하지 않는다.
- [x] `(match_id, reviewer_id, reviewee_id)` Unique 제약은 유지하며 마이그레이션에서 누락 시 중단하도록 검증한다.
- [x] 작성자·대상자 구분 Check와 `revisit_intention`·`impression_tag` 허용 코드 Check를 DB에 적용하고 검증한다.
- [x] 받은 후기 최신순 조회를 위해 `(reviewee_id, created_at DESC, id DESC)` 인덱스를 추가한다.
- [x] 공개 후기 집계 필터를 위해 `(reviewee_id, visibility, created_at DESC, id DESC)` 복합 인덱스를 추가한다.
- [x] 다시한끼 지수의 원본은 후기 레코드로 유지하고, 파생 점수만 재계산할 수 있게 설계한다.
- [x] MVP는 예상 트래픽과 일관성 요구를 고려해 별도 `user_review_summaries` 테이블 없이 집계 쿼리로 계산한다.
- [x] 요약 테이블은 MVP에서 사용하지 않는다. 향후 도입할 경우 후기 저장과 집계 갱신을 같은 트랜잭션에서 처리하고 전체 재계산 절차를 별도로 제공한다.
- [x] Entity 관계는 기본 LAZY로 유지하고 API 응답에는 Entity를 직접 노출하지 않는다. 조회 Projection·DTO 구현은 8번에서 적용한다.
- [x] 레거시 컬럼 삭제 마이그레이션 SQL과 백업·사전 검증·롤백·검증 절차를 [`docs/migrations/사용자_후기_컬럼_전환.sql`](../../migrations/사용자_후기_컬럼_전환.sql) 및 README에 추가했다.
- [x] 운영·개발 DB에서 `rating`·`content` 값이 0건이고 외부 의존성이 없는지 확인한 뒤 마이그레이션을 실행한다.

## 8. 백엔드 구현

- [x] `review/controller`, `service`, `repository`, `entity`, `dto` 구조를 유지한다.
- [x] 후기 작성 Service에 `@Transactional` 경계를 두고 참여자 검증, 대상자 결정, 중복 검증, 저장을 처리한다. 요약은 원본 후기 집계 쿼리로 계산하므로 별도 갱신 테이블을 사용하지 않는다.
- [x] 매칭 상태와 참여자 검증은 `MatchParticipationQueryService`를 통해 matching 도메인에서 수행하고 review가 matching Repository를 직접 호출하지 않는다.
- [x] `matchId`로 정확히 두 명의 `PARTICIPANT`가 확인되고 매칭 요청 소유자와 일치하는 경우만 저장하며, 비정상 데이터는 `REVIEW_DATA_INVALID`로 중단한다.
- [x] Controller는 인증 사용자 식별, DTO 검증, 상태 코드와 응답 변환만 담당한다. 작성·조회 책임은 Command/Query Controller와 Service로 분리한다.
- [x] 받은 후기 조회 Service는 `@Transactional(readOnly = true)`를 사용한다.
- [x] 지수 집계는 공개 후기만 한 번에 읽는 `ReviewScoreAggregateProjection`을 사용해 N+1 조회를 방지한다.
- [x] DB Unique 충돌을 `REVIEW_ALREADY_SUBMITTED`로 변환하고 SQL·내부 Entity 정보가 응답에 노출되지 않게 한다.
- [x] 애플리케이션 오류와 Bean Validation 메시지는 한국어로 작성한다.
- [x] 후기 구현에서 원문 전체, JWT, OAuth 식별자나 정밀 위치를 로그로 남기지 않는다.

## 9. 오남용·개인정보·공정성

- [x] 타인의 `matchId`를 추측해도 참여 여부와 상대 사용자 정보를 알아낼 수 없도록 존재하지 않는 매칭과 비참여 매칭을 모두 `404 COMMON_001`로 일반화한다.
- [x] 자기 자신을 대상으로 후기를 작성할 수 없게 참여자 결정 Service의 방어 검증과 `reviewer_id <> reviewee_id` DB Check를 함께 적용한다.
- [x] `MatchStatus.COMPLETED`만 후기 작성 대상으로 허용하고 `CANCELLED`를 포함한 그 밖의 상태와 한 사용자의 중복 제출을 서비스 검증·Unique 제약으로 차단한다.
- [x] MVP 지수 집계는 `visibility = PUBLIC`이고 Enum·작성자 구분 Check를 통과한 원본만 포함한다. `PRIVATE`는 제외하며, 삭제·신고 승인·운영상 무효화 상태는 해당 기능 도입 시 집계에서 제외하도록 별도 운영 TODO로 분리한다.
- [x] 작성자 식별자와 개별 답변은 응답에서 익명화하고, 유효 후기 3건 미만에는 점수를 노출하지 않아 단일 후기 작성자를 추론하기 어렵게 한다.
- [x] 다시한끼 지수는 API·Swagger·기능 명세에서 안전성·신뢰성을 보증하는 절대 척도가 아닌 참고 지표임을 안내한다.
- [x] 계정 생성 반복·담합 평가 탐지에 필요한 이벤트와 관리자 검토 범위를 개인정보 최소 수집 원칙과 함께 [`후기_오남용_운영_후속_TODO.md`](../진행중/후기_오남용_운영_후속_TODO.md)에 별도 정의한다.
- [x] 산식은 `ReviewScorePolicy.CURRENT_VERSION = DASI_HANKKI_V1`로 식별하고, 버전 변경 시 기존 집합을 재계산해 변경 전·후 불이익을 비교하는 절차를 문서화한다. 버전은 MVP 외부 응답에 노출하지 않는다.

## 10. 백엔드 테스트

- [x] 인증된 실제 참여자가 유효한 필수 답변만으로 후기를 작성할 수 있는지 테스트한다.
- [x] 네 가지 선택 태그 각각과 태그 미선택 제출을 서비스 테스트로 검증한다.
- [x] 필수 답변 누락, 알 수 없는 답변·태그와 잘못된 JSON에 `400`과 한국어 메시지가 반환되는지 테스트한다.
- [x] 미인증, 비참여자, 자기 자신 대상, 취소·작성 불가 매칭 상태와 작성 기한 만료를 테스트한다.
- [x] 동일 매칭·작성자·대상자 중복 제출을 두 스레드 경쟁으로 모의해 한 번만 저장되고 다른 요청은 DB Unique 충돌에서 `409`로 변환되는지 테스트한다.
- [x] 실제 PostgreSQL 독립 트랜잭션에서도 동일 경쟁의 저장 1건·`409` 결과를 확인한다. 현재 DB의 레거시 `rating NOT NULL` 제약 제거 마이그레이션 후 재검증한다.
- [x] 두 참여자가 서로에게 각각 한 번씩 작성할 수 있는지 서비스 테스트로 검증한다.
- [x] 다시한끼 지수의 후기 0건·1건·여러 건, 세 답변 조합, 반올림과 경계값을 단위 테스트한다.
- [x] 태그 미선택이 지수 산식에 전달되지 않는 Projection 계약과 점수 정책을 단위 테스트한다. 태그 통계는 MVP 외부 응답에서 제외한다.
- [x] 후기 무효화·수정·삭제 정책에 따라 지수와 태그 통계가 재계산되는지 테스트한다. 해당 상태 변경 기능은 운영 후속 TODO에서 정의한다.
- [x] 받은 후기 요약이 인증 사용자를 `reviewee`로만 집계하고 타인의 후기·작성한 후기를 섞지 않는지 서비스 테스트로 검증한다.
- [x] 공개 조회에서 비공개 원본 답변, 작성자 식별자와 민감 데이터가 제외되는지 테스트한다.
- [x] MVP에는 개별 후기 목록·페이지 API가 없어 동일 시각 정렬, 페이지 경계·최대 크기와 빈 목록 시나리오가 적용 대상이 아님을 확인했다. 목록 API 도입 시 별도 테스트한다.
- [x] PostgreSQL Enum 문자열, Check·Unique 제약과 집계 쿼리를 실제 DB 호환 환경에서 검증한다. 현재 DB에 `rating NOT NULL`이 남아 있어 컬럼 전환 마이그레이션 실행 후 검증한다.
- [x] Hibernate 로그에 `CommandAcceptanceException`과 스키마 생성 오류가 없는지 확인한다.

## 11. 마이페이지 연동 체크

- [x] raw Enum을 그대로 노출하지 않고 확정된 한국어 문구로 매핑한다.
- [x] 한 API 실패가 프로필·매칭 이력 등 다른 마이페이지 영역을 가리지 않게 한다.
- [x] 지수와 태그를 HTML로 주입하지 않고 안전한 텍스트로 렌더링한다.
- [x] 모바일·데스크톱, 긴 닉네임, 큰 후기 수와 소수점 표시를 확인한다.
