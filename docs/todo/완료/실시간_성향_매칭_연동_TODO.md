## 4. 양방향 후보 탐색과 프로필 제안 API

- [x] 후보 풀에는 인증된 사용자가 `POST /matches/realtime/requests`로 생성한 `WAITING` 요청만 포함한다.
- [x] 요청이 없는 사용자 프로필이나 과거·취소·만료 요청을 후보로 사용하지 않는다.
- [x] A의 요청으로 B를 탐색할 때 A의 조건만 적용하지 않고, B의 요청에서도 A를 허용하는지 하드 필터를 양방향으로 검증한다.
- [x] 거리 조건은 두 요청 핀 간 거리가 A와 B 각자의 탐색 반경 안에 모두 들어오는 경우에만 통과시킨다.
- [x] 식사 시간(+-30분) 조건이 어느 한쪽 기준만 만족하는 쌍을 제외한다. 음식 카테고리는 서로 달라도 후보로 허용한다. (차단 관계는 MVP 제외)
- [x] 양방향 하드 필터를 통과한 쌍에만 `A → B`, `B → A` 성향 호환도를 각각 계산한다.
- [x] 두 방향 점수를 최종 쌍 점수로 합성하는 정책(최솟값 우선 또는 평균과 편차 페널티)을 확정하고 산식 버전에 포함한다.
- [x] 한쪽 성향 데이터가 없으면 해당 방향은 기본 조건 점수로 fallback하되, 성향 미설정만으로 후보 쌍을 탈락시키지 않는다.
- [x] 후보 탐색 결과가 없으면 요청을 `WAITING`으로 유지하고 매칭 결과 알림이나 채팅방을 생성하지 않는다.

- [x] 양쪽 수락과 DB 트랜잭션 커밋이 완료된 경우에만 두 사용자의 인증 전용 `/user/queue/match-result`로 사용자별 결과를 전달한다.

- [x] 임베딩 동일·직교·반대 벡터와 모델·차원·버전 불일치 fallback을 테스트한다.
- [x] 임베딩 반영 비율이 최종 점수의 20%를 넘지 않는지 테스트한다.
- [x] 하드 필터 탈락 후보에 성향 계산기가 호출되지 않는지 테스트한다.
- [x] 성향 프로필·임베딩이 없는 사용자의 기본 매칭 성공을 테스트한다.
- [x] 매칭 요청 DTO와 Entity에 별도 식단 제한 필드가 없고 음식 카테고리가 일반 선호 조건으로만 처리되는지 테스트한다.
- [x] A만 수락한 상태에서는 `Match`와 `ChatRoom`이 생성되지 않고 결과 알림도 발송되지 않는지 lifecycle 테스트로 검증한다.
- [x] A와 B가 각각 요청하고 양방향 조건을 만족할 때 정확히 한 번만 매칭되는지 통합 테스트로 검증한다. (기존 DB role CHECK 마이그레이션 후 재실행 완료)
- [x] A 조건만 B를 허용하고 B 조건은 A를 허용하지 않을 때 매칭되지 않는지 테스트한다.
- [x] 후보 제안 응답에 허용된 간략 프로필만 포함되고 민감·내부 성향 데이터와 정밀 위치가 제외되는지 테스트한다.
- [x] 한쪽만 수락한 경우 매칭 데이터와 채팅방이 생성되지 않는지 lifecycle 테스트로 검증한다.
- [x] 양쪽이 순차 또는 동시에 수락해도 `Match`, 참여자 2명과 `ChatRoom`이 하나씩만 생성되는지 통합 테스트로 검증한다. (기존 DB role CHECK 마이그레이션 후 재실행 완료)
- [x] 어느 한쪽의 거절, 응답 만료, 요청 취소 후 늦은 수락으로 매칭이 생성되지 않는지 테스트한다.
- [x] 결정 API의 중복 수락·중복 거절 멱등성과 제안 당사자가 아닌 사용자의 접근 차단을 테스트한다.
- [x] A-B와 A-C 후보 쌍이 경쟁할 때 A가 두 매칭에 성사되지 않는지 테스트한다.
- [x] 확정 직전 취소·만료·다른 매칭 성사가 발생하면 해당 후보 쌍이 성사되지 않는지 테스트한다. (차단 관계는 MVP 제외)
- [x] 중복 요청의 멱등성(중복 레코드 미생성 및 명시적 충돌), 중복 대기, 취소, TTL 만료와 보상 처리 테스트를 작성한다.
- [x] 타인의 자유 서술·원본 응답·임베딩·정밀 핀 접근을 차단하는 보안 테스트를 작성한다.
- [x] PostgreSQL/PostGIS 기반 매칭 통합 테스트를 작성하고 Redis/WebSocket 호출은 테스트 대체로 격리한다.
- [x] API 계약을 `API명세서.md`, 기능 동작을 `기능명세서.md`와 동기화한다.
- [x] Java 변경 후 `gradlew.bat compileJava`와 `gradlew.bat test`를 실행한다.
- [x] 테스트 로그에서 `CommandAcceptanceException`과 Hibernate 스키마 생성 오류가 없는지 확인한다.

## 완료 조건

- [x] 동일 사용자가 동시에 두 개 이상의 활성 요청을 만들 수 없다.
- [x] 한쪽 사용자만 매칭 요청을 생성한 상태에서는 매칭 결과, 참여자 또는 채팅방이 생성되지 않는다.
- [x] 서로의 조건을 만족하는 두 활성 요청에 간략 프로필 제안이 전달되고 당사자만 조회·응답할 수 있다.
- [x] 양쪽 모두 제한 시간 안에 수락한 경우에만 정확히 한 번 매칭되며, 한 요청은 최대 한 매칭에만 사용된다.
- [x] 거절·응답 만료·취소된 제안은 매칭을 만들 수 없고 유효한 요청은 정책에 따라 다시 대기할 수 있다.
- [x] 두 방향의 성향 호환도와 최종 쌍 점수를 동일한 요청 스냅샷과 산식 버전으로 재현할 수 있다.
- [x] 모든 후보는 하드 필터를 통과한 뒤에만 성향 점수를 받는다.
- [x] 성향·AI 데이터가 없어도 기본 위치·시간 매칭이 정상 동작한다.
- [x] 별도의 식단 제한 정보를 수집·저장·추론하지 않으며 음식 카테고리를 식단 안전성 보장으로 표시하지 않는다.
- [x] 최종 점수와 사용자용 사유를 동일한 입력과 산식 버전으로 재현할 수 있다.
- [x] 매칭 확정 시 참여자는 정확히 두 명이며 참여자만 결과와 채팅방에 접근할 수 있다.
- [x] 운영 마이그레이션, API 문서, 테스트와 실제 Entity 매핑이 일치한다.
