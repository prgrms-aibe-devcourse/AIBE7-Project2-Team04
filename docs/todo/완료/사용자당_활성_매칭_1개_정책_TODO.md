# 사용자당 활성 매칭 1개 정책 TODO

> 한 사용자는 동시에 하나의 확정 매칭(`Match.status = MATCHED`)에만 참여할 수 있다. 활성 매칭이 종료되기 전에는 새 실시간 매칭 요청과 후보 선정을 모두 차단하고, 프론트엔드는 현재 매칭과 채팅방으로 사용자를 안내한다.

## 목표

- 한 사용자에게 둘 이상의 활성 매칭과 활성 채팅방이 생기지 않도록 서버에서 보장한다.
- 활성 매칭이 있는 사용자가 홈이나 매칭 페이지로 다시 진입해도 과거 결과를 새 매칭 결과처럼 표시하지 않는다.
- 확정 전 `매칭 요청 취소`와 확정 후 `매칭 종료`를 서로 다른 상태 전이와 API로 처리한다.
- 매칭 종료 시 매칭과 채팅방 상태를 함께 종료하고, 양쪽 사용자 화면에 일관되게 반영한다.
- 프론트엔드 검사를 우회하거나 동시 요청이 발생해도 서버가 정책을 최종 보장한다.

## 현재 확인된 문제

- [x] 매칭 요청 생성 시 `WAITING`, `CONFIRMING` 요청만 중복 검사하고 활성 `Match.status = MATCHED`는 검사하지 않는다.
- [x] `GET /matches/realtime/results/latest`는 상태와 관계없이 가장 최근 매칭을 반환하므로 활성 매칭 판정 용도로 사용하기 어렵다.
- [x] 매칭 완료 화면의 `새 매칭 요청`은 프론트엔드 로컬 상태만 초기화하고 서버의 기존 매칭 상태를 종료하지 않는다.
- [x] `MatchStatus`에는 `MATCHED`, `COMPLETED`, `CANCELLED`가 있지만 확정 매칭을 종료하는 서비스·API가 구현되어 있지 않다.
- [x] 매칭 종료 후 채팅방을 `CLOSED`로 전환하는 요구사항은 있으나 매칭 종료 흐름과 아직 연결되어 있지 않다.

## 정책과 상태 기준

- [x] `MATCHED`를 새 매칭을 차단하는 유일한 활성 매칭 상태로 확정한다.
- [x] `COMPLETED`, `CANCELLED`를 새 매칭 요청이 가능한 종료 상태로 확정한다.
- [x] `WAITING`, `CONFIRMING` 상태의 `MatchRequest`가 있으면 기존과 같이 새 요청을 차단한다.
- [x] 확정 전에는 `매칭 취소`, 확정 후에는 `매칭 종료`라는 사용자 문구와 도메인 용어를 사용한다.
- [x] 한쪽 참여자가 매칭 종료를 요청하면 양쪽 모두에게 즉시 적용하고, 상대방에게 종료 사실을 알리는 정책을 확정한다.
- [x] 종료된 매칭과 채팅 메시지는 이력으로 보존하고 새 매칭 가능 여부 계산에서만 제외한다.
- [x] 동일 사용자의 종료된 과거 매칭은 활성 매칭 수 계산에 포함하지 않는다.
- [x] (선택) 매칭 종료 직후 같은 상대와 다시 매칭되지 않도록 최근 상대 재매칭 제한 기간을 정한다. -> 개발 단계에서 테스트 목적으로 제외.

## 1. 데이터 모델과 상태 전이

- [x] `Match`에 `MATCHED -> COMPLETED`, `MATCHED -> CANCELLED` 상태 전이 메서드를 추가한다.
- [x] 이미 `COMPLETED` 또는 `CANCELLED`인 매칭을 다시 활성화하거나 다른 종료 상태로 덮어쓰지 못하게 한다.
- [x] 매칭 종료 시각을 `ended_at` 컬럼으로 보존한다. 활성 `MATCHED` 상태에서는 NULL로 유지한다.
- [x] 종료 요청자와 종료 사유는 현재 정책에서 저장하지 않는다. 필요 시 별도 감사 이력 정책으로 확장한다.
- [x] `ChatRoom`은 `ACTIVE -> CLOSED` 단방향 전이와 `closedAt` 정합성 검증을 제공한다.
- [x] 매칭 종료와 채팅방 종료가 하나의 트랜잭션에서 성공하거나 함께 롤백되도록 한다.
- [x] 운영 DB 스키마 변경이 필요하면 안전한 마이그레이션 SQL을 `docs/migrations/`에 추가한다. 현재 MVP는 `ddl-auto=update` 정책을 따른다.
- [x] Entity와 DDL 변경 내용을 `데이터모델링.md`, `스키마요약.md`에 동기화한다.

## 2. 활성 매칭 조회 기준

- [x] 참여자 UUID와 `Match.status = MATCHED`를 기준으로 활성 매칭을 조회하는 Repository 쿼리를 추가한다.
- [x] 활성 매칭 조회 시 `MatchParticipant`, 상대 사용자, `ChatRoom`을 필요한 범위에서 함께 조회하여 N+1 쿼리를 방지한다.
- [x] 사용자별 활성 매칭이 둘 이상 발견되면 임의의 한 건만 숨기지 말고 데이터 정합성 오류로 기록·처리한다.
- [x] 기존 `GET /matches/realtime/results/latest`는 WebSocket 유실 복구와 이력 조회 의미로 유지하고 활성 매칭 판정에 사용하지 않는다.
- [x] 활성 매칭 전용 조회 API 경로를 확정한다. 예: `GET /matches/current`.
- [x] 활성 매칭 응답에 `matchId`, `status`, `chatRoomId`, 상대방 공개 프로필, 매칭 시각을 포함한다.
- [x] 활성 매칭이 없을 때 반환할 상태 코드와 오류 코드 계약을 확정한다.

## 3. 새 매칭 요청 서버 차단

- [x] `POST /matches/realtime/requests` 처리 전에 인증 사용자에게 활성 `MATCHED` 매칭이 있는지 검사한다.
- [x] 활성 매칭이 있으면 `409 Conflict`와 별도 오류 코드(예: `MATCHING_014`)를 반환한다.
- [x] 오류 메시지는 `현재 진행 중인 매칭을 종료한 후 새 매칭을 요청할 수 있습니다.`처럼 한국어로 제공한다.
- [x] 활성 매칭 검사 후에만 Redis 사용자 예약 키와 새 `MatchRequest`를 생성한다.
- [x] 활성 매칭 차단으로 요청이 거절될 때 Redis 예약 키나 DB 요청 행이 남지 않도록 한다.
- [x] 기존 활성 요청 중복 오류(`MATCHING_003`)와 활성 확정 매칭 오류를 구분한다.
- [x] 프론트엔드 요청을 우회한 직접 API 호출에서도 동일하게 차단되는지 검증한다.

## 4. 후보 탐색과 매칭 확정 동시성

- [x] 후보 검색 쿼리에서 양쪽 사용자 모두 활성 `MATCHED` 매칭이 없는 경우만 후보로 사용한다.
- [x] 제안 생성 직전에 두 사용자의 활성 매칭 여부를 다시 검사한다.
- [x] 양쪽 수락 후 `Match` 생성 직전에 참여 사용자 기준으로 활성 매칭 여부를 다시 검사한다.
- [x] 사용자 또는 사용자별 활성 매칭 슬롯을 UUID 정렬 순서로 잠가 교착과 중복 확정을 방지한다.
- [x] 동일 사용자의 서로 다른 요청이 동시에 확정되려는 경우 정확히 한 건만 `MATCHED`가 되도록 통합 테스트한다.
- [x] 경쟁에서 패한 요청·제안은 정책에 맞는 종료 또는 대기 복귀 상태로 전환한다.
- [x] 서비스 잠금만으로 충분한지 검토하고, 필요하면 사용자별 활성 매칭 슬롯 테이블이나 DB 제약을 도입한다.
- [x] 후보 검색 스케줄러와 Redis 복구 작업에서도 활성 매칭 사용자를 대기열로 되살리지 않도록 한다.

## 5. 확정 매칭 종료 API

- [x] 매칭 참여자 전용 종료 API 경로를 확정한다. 예: `PATCH /matches/{matchId}/cancel`.
- [x] 인증 사용자가 해당 매칭의 실제 참여자인지 검증한다.
- [x] `MATCHED` 상태만 종료할 수 있고 타인의 매칭 종료 요청은 `403 Forbidden`으로 차단한다.
- [x] 동일 사용자의 종료 요청 재전송은 멱등하게 처리한다.
- [x] 동시에 양쪽 사용자가 종료를 요청해도 상태 전이와 채팅방 종료가 한 번만 수행되도록 잠근다.
- [x] 매칭을 `CANCELLED`로 전환하면서 연결된 채팅방을 `CLOSED`로 전환한다.
- [x] 종료된 채팅방에 대한 새 메시지 전송을 서비스와 WebSocket 메시지 처리 단계에서 차단한다.
- [x] 종료된 채팅방의 신규 구독 정책과 기존 연결 세션 정리 정책을 확정한다.
- [x] 종료 후 과거 메시지 읽기를 허용할지 제품 정책을 확정하고 조회 API에 반영한다.
- [x] 매칭 종료 커밋 후 상대방에게 개인 WebSocket 이벤트를 전송한다. 예: `/user/queue/match-status`.
- [x] WebSocket 이벤트 유실 시 활성 매칭 조회 API 재호출로 상태를 복구할 수 있게 한다.
- [x] 종료 API의 성공·실패·멱등 응답과 오류 코드를 `API명세서.md`에 정의한다.

## 6. 홈 화면 프론트엔드

- [x] 로그인 사용자의 홈 진입 시 활성 요청과 활성 매칭 상태를 조회한다.
- [x] 활성 매칭이 있으면 기본 `매칭` CTA를 `현재 매칭 보기` 또는 `채팅방 입장`으로 변경한다.
- [x] 활성 매칭이 있는 동안 지도 선택과 새 매칭 요청 진입 버튼을 비활성화하거나 현재 매칭 화면으로 안내한다.
- [x] 활성 요청만 있는 경우 `매칭 대기 상태 보기`와 `매칭 요청 취소` 경로를 제공한다.
- [x] 상태 조회 중에는 중복 클릭과 화면 깜빡임을 줄이는 로딩 상태를 표시한다.
- [x] 활성 상태 조회 실패를 `새 매칭 가능`으로 간주하지 않고 재시도 가능한 오류로 안내한다.

## 7. 매칭 페이지 프론트엔드

- [x] 매칭 페이지 최초 진입 시 활성 매칭 전용 API를 가장 먼저 확인한다.
- [x] 활성 매칭이 있으면 새 요청 폼 대신 상대방 요약, `채팅방 입장`, `매칭 종료` 버튼을 표시한다.
- [x] 기존 매칭 완료 화면의 `새 매칭 요청` 버튼은 활성 매칭을 종료하지 않은 상태에서는 제거하거나 비활성화한다.
- [x] `GET /matches/realtime/results/latest`의 과거 결과만으로 활성 매칭 화면을 결정하지 않는다.
- [x] 직접 URL로 매칭 요청 페이지에 접근해도 활성 매칭이 있으면 요청 폼을 제출할 수 없게 한다.
- [x] 서버가 활성 매칭 충돌 `409`를 반환하면 폼 상태를 복구하고 현재 매칭 화면으로 전환한다.
- [x] `매칭 종료` 클릭 전에 상대방 채팅 종료와 새 매칭 가능 상태로 전환된다는 확인 문구를 표시한다.
- [x] 종료 요청 중 중복 클릭을 막고 성공 후 기존 상대방·채팅방 상태를 화면에서 정리한다.
- [x] 종료 성공 후에만 새 매칭 요청 폼과 지도 선택 경로를 다시 활성화한다.
- [x] 상대방이 매칭을 종료한 WebSocket 이벤트를 받으면 현재 화면과 버튼 상태를 즉시 갱신한다.
- [x] WebSocket 재연결 시 활성 매칭 API로 최종 상태를 재동기화한다.

## 8. 채팅 화면 프론트엔드

- [x] 채팅방 입장 시 연결된 매칭이 여전히 `MATCHED`인지 확인한다.
- [x] 채팅 화면에 `매칭 종료` 진입점을 제공할지, 현재 매칭 화면으로 이동시킬지 결정한다.
- [x] 종료된 채팅방에서는 메시지 입력과 전송 버튼을 비활성화한다.
- [x] 상대방의 종료 이벤트를 받으면 `매칭이 종료되어 더 이상 메시지를 보낼 수 없습니다.` 안내를 표시한다.
- [x] 종료 직전에 작성 중이던 메시지가 전송 실패한 경우 사용자에게 명확히 안내한다.
- [x] 과거 메시지 조회를 허용하는 경우 읽기 전용 화면임을 표시한다.

## 9. 보안과 개인정보

- [x] 활성 매칭·종료 API는 인증을 필수로 하고 참여자 이외의 접근을 차단한다.
- [x] 활성 매칭 조회 응답에는 공개 프로필과 필요한 식별자만 포함하고 정밀 위치·OAuth 식별자·토큰을 포함하지 않는다.
- [x] 매칭 종료 로그에 채팅 내용, 토큰, 상대방의 비공개 프로필 정보를 기록하지 않는다.
- [x] CSRF 보호가 활성 매칭 종료 API에도 적용되는지 검증한다.
- [x] CORS와 WebSocket Origin 정책을 변경하지 않고 기존 프론트엔드 Origin 정책을 유지한다.
- [x] 오류 응답으로 타인의 활성 매칭 여부나 내부 식별자가 노출되지 않도록 한다.

## 10. 백엔드 테스트

- [x] 활성 `MATCHED` 매칭이 있는 사용자의 새 요청이 `409`로 거절되는 서비스·컨트롤러 테스트를 작성한다.
- [x] `COMPLETED`, `CANCELLED` 매칭만 있는 사용자는 새 요청을 생성할 수 있는지 테스트한다.
- [x] 활성 요청과 활성 매칭 오류가 서로 다른 오류 코드로 반환되는지 테스트한다.
- [x] 활성 매칭 사용자가 후보 검색 결과에서 양방향으로 제외되는지 테스트한다.
- [x] 서로 다른 두 요청이 동일 사용자를 동시에 매칭시키려 할 때 하나만 성공하는 동시성 테스트를 작성한다.
- [x] 참여자만 매칭 종료가 가능하고 비참여자는 차단되는지 테스트한다.
- [x] 매칭 종료와 채팅방 종료가 원자적으로 처리되는지 테스트한다.
